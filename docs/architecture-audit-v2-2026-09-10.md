## 第三部分：架构风格分析

**当前架构：** 模块化单体 + 事件驱动组件

### 优点
- 单进程部署简单，调试方便
- 模块边界清晰（P0-P5 重构后）
- 事件驱动解耦了通知和业务逻辑
- 自动备份 + 容器化提升了运维能力

### 缺点
- 所有后台任务共享进程，一个崩溃全部停止
- SQLite 单文件限制并发和备份
- 无水平扩展能力

### 适用性评估

| 维度 | 评估 |
|------|------|
| 当前规模（1-5 agents） | ✅ 完全适用 |
| 未来增长（10+ agents） | ⚠️ 需迁移 PostgreSQL |
| 团队能力（小团队） | ✅ 可维护 |
| 运维能力（本地/容器） | ✅ 已支持 Docker |

```

```
模块：transitions.py 桥接函数 (27 个调用点)

当前影响：每个使用状态的地方都需要调用桥接函数
未来风险：新增特殊映射值时需要修改 27 个调用点

## 第九部分：性能架构分析

### 完整请求链路

```
Client (React SPA)
  ↓ HTTP/WebSocket
FastAPI (sync endpoints in threadpool)
  ↓ SQLModel ORM
SQLite (WAL mode, QueuePool 5-15)
  ↓ (optional)
External: MCP Server / Git / Webhook
```

### 性能瓶颈 TOP 10

| # | 位置 | 瓶颈原因 | 影响 | 优化 |
|---|------|----------|------|------|
| 1 | SQLite WAL checkpoint | 高频写入后 WAL 文件膨胀 | 写入延迟增加 | 定期 checkpoint |
| 2 | `board.py` 聚合查询 | 每次请求执行 5+ 个 COUNT 查询 | 首页加载慢 | 缓存 5s |
| 3 | `_task_detail()` | 60 行函数执行 6 个子查询 | 单任务详情慢 | 预加载/缓存 |
| 4 | Memory JSONL 全表扫描 | 无索引，O(n) 查询 | 知识查询慢 | 迁移 SQLite FTS5 |
| 5 | WebSocket 广播同步 | `asyncio.run()` 在同步上下文 | 事件广播延迟 | 改为异步路径 |
| 6 | Cron engine 10s 轮询 | 固定间隔，无法更精细 | 任务触发延迟 | 改为事件驱动 |
| 7 | 前端 5s 轮询 | WebSocket 断开时降级为轮询 | 实时性差 | 增加重连优先级 |
| 8 | `advance_stage` 重复代码 | ~80% 与 `move_to_stage` 重复 | 维护成本高 | 提取共享逻辑 |
| 9 | 无查询缓存 | 重复查询无优化 | 相同数据重复计算 | 内存缓存 |
| 10 | 无连接池监控 | 资源泄漏不可见 | 潜在性能退化 | 添加 metrics |

## 第十七部分：CTO 最终结论

### 架构最大优势
**状态机驱动的业务规则不可绕过 + 自动备份保证数据安全。** 21 种显式转换 + 验证器确保了所有状态变更都经过严格校验。SQLite Online Backup API 保证了每小时一致性强 snapshot。这是系统最核心的两个架构决策。

### 当前最大风险
**`api/tasks.py` 的 671 行 God Controller 和 `mcp_server.py` 的 797 行薄代理。** 这两个文件是未来 6-12 个月最可能成为维护瓶颈的代码。

### 最错误的三个设计
1. **`mcp_server.py` 797 行手动编写** —— 每个 MCP 工具都是 HTTP 转发样板代码，应从 OpenAPI 自动生成
2. **`api/tasks.py` 671 行未拆分** —— 19 个端点 + 业务逻辑堆在一个文件
3. **桥接函数 27 个调用点** —— 应封装为 Task model 的 @property 方法

### 最值得投入的三个优化方向
1. **P2：** 拆分 `api/tasks.py`（1 天，消除 God Controller）
2. **P2：** 从 OpenAPI 自动生成 MCP 工具（2 天，消除 797 行重复代码）
3. **P2：** 全局 API 限流（0.5 天，消除安全风险）

## 架构演进路线

### 0-3 个月（当前）
**已解决：** 数据安全（自动备份）+ 部署灵活性（Docker）+ 状态统一
**下一步：** 拆分 God Controller + MCP 自动生成 + API 限流

### 3-6 个月
**建设：** 代码质量 + 可观测性
- `api/tasks.py` 拆分为 3 个模块
- `mcp_server.py` 从 OpenAPI 自动生成
- 全局 API 限流
- OpenTelemetry 分布式追踪

### 6-12 个月
**优化：** 扩展能力 + 自动化
- 测试覆盖率提升至 80%+
- CI/CD 增加 lint + type check + coverage
- Staging 环境自动部署
- 桥接函数封装为 @property

### 1-3 年
**目标架构：** 如需多用户/高并发
- SQLite → PostgreSQL 迁移
- 单进程 → 多进程/微服务
- 本地部署 → 容器化部署
- 添加 API 网关 + 认证服务
