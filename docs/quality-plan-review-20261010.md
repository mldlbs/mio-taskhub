# 《mio-taskhub AI 代码质量提升方案》评审意见

- **评审对象：** `mio-taskhub AI 代码质量提升方案` v0.1（13 节）
- **评审日期：** 2026-10-10
- **评审基线：** commit `1e7d00e`，分支 `task-516bd0c7`
- **评审范围：** 方案本身（问题定义、逻辑一致性、优先级排序、可执行性），**不含实施**
- **证据口径：** 沿用方案 §5.3 的四分法 —— 已证实 / 已复现 / 待核查 / 设计建议

---

## 1. 总体判断

- **方向正确。** §1.1 把「执行成功 / 任务完成 / 代码合格」切成三件事，是这个方案最值钱的一句话；§1.3 把「用 LLM 自我评分代替质量判断」明确列为非目标，拦住了一个大坑。
- **但这是一份「体检表写得比处方好」的方案。** 全文 13 节里，描述「应该有什么」的篇幅约占七成，可直接执行的举措集中在 §7.4 一张表和 §9 五条优先级。
- **最大的问题不在内容，在排序。** 方案把两类完全不同的工作并列成了同一条列表：
  - 「从 0 到 1」：变更识别、测试执行、评审身份隔离 —— 当前系统**完全不具备**；
  - 「从 1 到 1.1」：失败分类、评分报告、趋势分析 —— 有基础设施，只差打磨。
  - 两者并列会导致阶段四的改造顺序出错（详见 §4）。
- **另一个结构性问题：指标集与系统前提不匹配。** §8 的「交付缺陷率 / 回归缺陷率」在「本地单用户、无生产环境、无用户报障」的前提下**采不到数据**（详见 §3.5）。

一句话结论：**这份方案可以采纳，但建议先按本文 §4 重排优先级、按 §6 收敛成三份文档，再做阶段三。**

## 3. 逻辑问题（逐条）

### 3.1 阶段顺序与 §13 自相矛盾

- §9 把「阶段一：冻结质量标准」排在最前；§13 第 1 条也写「确定标准」。
- 但 §13 正文又说：「**当前最重要的不是立即实现综合评分系统，而是确认现有执行链是否具备可信的代码交付验收能力。**」
- 两句话是冲突的。在没有审计的情况下冻结标准，会直接导致标准里塞满**无法采集的判据**——因为写标准的人不知道系统能采到什么。
- **建议顺序：** 快照审计（约 1 人次） → 冻结标准 → 深度审计。审计应先于标准，因为它的核心产出之一就是「哪些判据有机器证据支撑」这份输入。

### 3.2 「七维度加权总分」与「硬缺陷优先」内在冲突

- §2.2 明确「硬性缺陷优先于综合评分」，§3.1 又给出加权 100 分。
- 两套机制并存时，总分在实践中一定会被当成放行依据——这正是 §1.3 自己反对的「用单一分数代替工程判断」。
- **建议：** 二选一。推荐删掉总分，只保留「阻断项清单 + 分维度定性等级」。若确需总分用于趋势，必须在文档里显式标注「仅用于统计，不参与放行判断」。

### 3.3 权重以精确数字呈现，但自称待校准

- §3.1 标注「初始权重只是待验证假设」，却写成 25/20/15/15/10/10/5。
- 小数点级的精度会制造权威错觉，而方案自己承认这些数字没有依据。
- **建议：** 校准前只保留**排序**（正确性 > 设计 > 可理解性 ≈ 可维护性 > 测试 ≈ 安全 > 规范），不写数字；数字在校准阶段回填。

### 3.4 阻断项缺少「执行方式」标注

- §3.3 第一条阻断项「**实际代码变更与提交结果声明不一致**」写得很好，但系统当前**没有能力识别代码变更**（§2 表第 2 行）。
- 这意味着这条阻断项目前只能人工目视，而方案没有区分这一点。
- **建议：** §3.3 每条阻断项增加一列 `执行方式：机器 / 人工 / 暂不可执行`。否则阶段四会做出「声称实现了校验、实际靠肉眼」的假闭环——这正是方案自己极力反对的东西。

### 3.5 指标集与「本地单用户」前提不匹配（最实际的问题）

§8 已经自省了「先定义分母」，但表格本身没有给分母，且至少两项**在当前前提下采不到数**：

| 指标 | 问题 |
|---|---|
| 交付缺陷率 | 「交付后发现的缺陷」需要生产环境 + 用户报障。本系统是本地单用户、零联网、无线上环境 → **永远为 0 或不可知** |
| 回归缺陷率 | 同上，需要「变更后既有行为出问题」的外部反馈源 → **采不到** |

- **建议：** 删掉这两项，改为在当前前提下**可采集**的代理指标：

| 替代指标 | 采集方式 |
|---|---|
| 首次验收通过率 | 首次 `submit_review(approve)` 前的 `reject` 次数 |
| 返工率 | 同一 task 的 run 数量分布 |
| 绕过率 | 带 `force=true` / `MIO_*` 豁免的事件计数（系统已有事件流，可直接统计） |
| 验证有效率 | 注入已知缺陷，看验证项能否发现 —— 这是唯一能证明「检查有价值」的指标 |

- 「验证有效率」是方案 §8 里唯一定义正确的指标，建议把它升为**实验期的核心指标**：它回答的是「这些闸门到底值不值」，而不是「我们跑了几次」。

### 3.6 §10 测试清单缺少「时间维度」

§10 列了 8 类测试，覆盖了空间维度（不同路径），但没有一条对应**时间维度**：

- 证据过期后失效（§10.4 提了版本一致性，但没提「过期」如何触发）
- Hub 重启后旧 run 的证据是否仍生效
- 长任务跨天、跨版本时的证据有效性

- **建议：** 补一条 `9. 证据时效：跨 Run / 跨重启 / 跨版本时，旧证据必须失效并重新采集`。

## 4. 优先级重排（针对 §9 阶段四）

方案原文把 5 条并列。按「是否为 0→1」重排如下：

### P0 —— 不做则整个质量方案是空的

| # | 改造项 | 为什么是 P0 |
|---|---|---|
| 1 | **变更识别**：Run 绑定实际 diff（基线 + changed files） | §6.2 与 §7.3「证据绑定变更」的前提。没有它，所有「证据」都只能证明「文档被读过」，不能证明「代码改了什么」 |
| 2 | **测试结果绑定**：Agent 提交「测试命令 + 输出 + 代码版本 sha」，服务端校验 sha 与提交时一致 | 当前 `submit_result` 只看一个 `success: bool`，是最大的可信度缺口 |
| 3 | **评审身份隔离**：`reviewer` 必须 ≠ `run.agent_name`，或显式标记为 self-review | §6.5「独立验收」的成立条件。现在同一 agent 可以自己 approve |

### P1 —— 在 P0 之上才有意义

| # | 改造项 |
|---|---|
| 4 | `read_evidence` 扩展到代码版本维度（现在只指纹文档） |
| 5 | 失败分类 → 修复 → 重测闭环（§6.6） |

### P2 —— 有了数据再谈

| # | 改造项 |
|---|---|
| 6 | 评分、报告、趋势分析（§8 的采集端） |

**排序理由：** P0 三项都是「系统完全不具备该能力」，P1/P2 是「有基础设施、差打磨」。原方案的排序会让 P2 的类型工作（评分报告）与 P0（变更识别）并列，容易先做出好看但无用的仪表盘。
