## 0. 阅读约定与本计划的纪律

**证据分档**（沿用 `01`/`02`/`03`/`04` §0）：**事实** = 代码/命令/DB 直接证明（附码位/命令）；**推断** = 由实现推出（标「（推断）」）；**待验证** = 待本计划产出的证据（标「（待验证）」）。

**四条纪律（本计划自身的防自欺规则）**：

1. **门先行**：每个阶段有唯一 **Gate**；Gate 未过不得进入下一阶段，也不得以"部分完成"名义软化判据。
2. **判据可执行**：每个任务的完成定义（DoD）必须绑定一条**可复现命令或其输出**；无法用证据判定的条目不得进入任务表。
3. **无口号**：任何任务若不能写出"不成立的失败形态"，则退回重写（对齐 `03` §0 自律 3）。
4. **门禁指标排除分发**：Star / Trending 只能作为 §6 的**观测指标**，**不得**出现在 G0–G4 任一 Gate 的通过条件里。

**任务字段规范（转 taskhub 时的强制字段）**：`标题 / 前置依赖(depends_on) / 涉及模块(files) / 验收命令(acceptance_criteria) / 完成定义(DoD) / 风险 / 成本 / 上游映射`。见 §7 转换模板。

## 1. 计划总览：五阶段五门

> 主线逻辑（对齐 `03` §5.2 依赖关系）：**先修验证链与证据缺口（G0）→ 让实验能跑（G1）→ 让结论成立（G2）→ 据结论决定产品化范围（G3）→ 达标才发布（G4）**。
> **功能增量的唯一开关在 G2**：G2 之前任何阶段**不新增产品功能**（只做修复与观测脚手架），这正是 `01` D2 决策 + `03` §6.1 十项停/冻的执行化。

| 阶段 | 名称 | Gate 判定 | 主要产出 | 是否允许新增功能 |
|---|---|---|---|---|
| **G0** | 证据链修复与审计通过 | **审计通过** | CI 绿 / 覆盖率 / 文档入库 / 生命周期埋点 / 基线冻结 | 否（仅修复+观测） |
| **G1** | 实验可运行 | **实验可运行** | 实验 harness / 档位探针 / 复现一致 / 审批到位 | 否（仅验证性代码） |
| **G2** | 实验结论成立 | **实验结论成立** | M/B/P 三态判定 / D1 根因报告 / 回写 01⊕03 | 否（只出结论） |
| **G3** | 产品化完成 | **产品化完成** | D1 固化 ± D2-b ± D3（条件性）/ 开源前置 / 首跑门槛 | **是（依 G2 结论）** |
| **G4** | 发布准备完成 | **发布准备完成** | Release / 可复现构建 / 干净机验证 | 否（只打包） |

**阶段间关系（事实，来自上游）**：

- G0 的 D1 埋点是 `03` §4 D1 的"待实施"部分，设计已过两轮评审（`docs/taskhub/design-agent-lifecycle-instrumentation.md` A1–A5），边界固化（不改 reaper/timeout/门控/事务）。
- G1/G2 的判据**预注册在 `04`**（H1–H8、S1–S7、§7 三态），本计划不新增、不放松任何判据；`04` §9 的 P1–P5 即 G1 的准入清单。
- G2 的三条结论（D1 首启达标、V1 门控效应、V2 质量效应）分别驱动 G3 的 D1 固化、D2-b、以及"门控降级为可选"分支（`03` §7）。

## 7. 时间估算（单人、含假设与不确定性）

**估算口径**：单人 + agent 辅助、**熟悉本仓库**、含设计/实现/测试/取证；**不含**外部评审等待、审批墙钟、分发运营。
**墙钟与工时分列**：样本采集类是墙钟依赖，与并行任务重叠，不计入纯工时。

| 阶段 | 纯工时（人周） | 墙钟依赖 | 不确定性 |
|---|---|---|---|
| G0 证据链修复 | **3–4 周** | reaper 样本 2–4 周 | CI 首次绿可能暴露新 flaky；埋点可能失效 |
| G1 实验可运行 | **3–4 周** | 审批 P3/P4 | harness 复现一致性；审批 defer 会改变路径 |
| G2 结论成立 | **4–6 周** | B 系列样本 4 周封顶；D1 生产样本 2–4 周 | 样本自限（n16 教训）；D1 根因可能在项目外 |
| G3 产品化 | **3–5 周** | D2-b/D3 条件性 +3–12 周 | 外部接入者是否出现 |
| G4 发布准备 | **1–2 周** | 干净机外部验证 | 构建环境漂移 |
| **基线路径合计** | **≈14–21 人周（约 3.5–5 个月）** | — | — |
| **含 D2-b + D3** | **+6–12 周**（条件性） | 6 个月观察窗 | — |

**估算假设（必须随计划交付）**：

1. **单人全职**语义（约 5 工作日/周）；兼职需按比例放大。
2. D1 埋点设计**已完成**（`03` §4），故工时低于其 1–2 周上限之外的新增设计；若评审推翻设计，G0 工时上浮。
3. **不含**跨人协作、正式评审排期、GitHub 发布审核的等待时间。
4. **样本量与墙钟**：`04` §5.1 的 n≥100 首启、n≥30/组 等为**自然样本**，禁止人工造样本（`03` §5.2 纪律）。
5. D2-b/D3 **不计入基线**——它们是 G2 通过后的条件增量。

**主要不确定性（按影响排序）**：

| # | 不确定性 | 影响 | 缓解 |
|---|---|---|---|
| U1 | D1 根因落在项目外（agent CLI/环境） | G2 无法给"修复有效"结论 | 预置"诊断可读化"出口（`03` §7 D1 部分成立） |

## 9. 验收指标纪律：Star / Trending 不得作为阶段门指标

> 这是题目与本计划共同要求的硬约束，也是 `01` §5.4 的决策化。

2. **允许的用途（仅观测）**：作为**领先指标**记录，用于决定是否**另行**投入分发（非研发阶段验收）：

|---|---|---|
| Star 周增速 | ≥15/周 持续 2 周 | `01` §5.4 |

| 外部真实闭环使用者 | ≥3 人 | `01` §5.3 G5 |

3. **判据方向说明**：研发阶段的验收一律是**技术证据**（可复现命令、DB 事件、实验三态结论、CI 结果）；分发指标只影响"是否讲增长故事"，**不影响**任何阶段能否通过。

## 11. 任务转 taskhub 模板（保证"可直接转成项目任务"）

> 每个任务卡按下列字段映射到 `taskhub_create_task`，`acceptance_criteria` 直接取任务卡的"验收命令 + DoD"。

```json
{
  "title": "<任务卡标题>",
  "description": "<目标 + 涉及模块(码位) + 上游映射>",
  "acceptance_criteria": "<DoD 原文 + 可复现验收命令原文>",
  "depends_on": ["<上游任务 id>"],
  "files": ["<涉及模块路径>"],
  "priority": "<0-3，按阶段顺序>",
  "stage": "brainstorming | design | planning | ready",
  "project": "mio-taskhub",
  "labels": ["roadmap-05", "G<0-4>", "<F/D/E/H 编号>"]
}
```

**转换规则**：

1. 阶段内任务按 T 编号顺序转；跨阶段依赖用 `depends_on` 显式声明（如 T2.1 depends_on G1 全部任务）。
2. 凡**条件性**任务（T3.2/T3.3）在创建时标注 `labels += ["conditional"]`，**前置结论未出前不得进 `ready`**。
3. 每个任务的 `acceptance_criteria` 必须包含一条**可复现命令**；无命令的条目不得创建（§0 纪律 2）。

## 结论（可复述版）

1. **五阶段五门**：G0 审计通过 → G1 实验可运行 → G2 结论成立 → G3 产品化 → G4 发布准备；每门有可执行判据与"继续/返工/调整/停止"处置。
