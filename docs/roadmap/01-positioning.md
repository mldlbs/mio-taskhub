## 0. 阅读约定（证据分档）

沿用本仓库 `docs/taskhub/assessment-guidelines.md` 的铁律，全文每条关键判断必须落在三档之一：

| 档位 | 含义 | 允许的写法 |
|---|---|---|
| **事实** | 代码、数据、命令输出或公开来源**直接**证明 | 给出可复核的路径/命令/链接 |
| **推断** | 由实现或数据推断，**无直接证明** | 写"（推断）"，并给出推断链 |
| **待验证** | 目前缺证据，是主张/假设 | 写"（待验证）"，并给出验证方法 |

禁止："看起来应该""理论上""大概率"。**不越界**：把推断写成事实，比少写更有害。

## 2. 核心问题、目标用户、核心场景

### 2.1 核心问题（事实 + 推断）

| # | 问题 | 档位 |
|---|---|---|
| P1 | 多个 AI 编程助手各自为战，**任务归属、在线状态、进度、重试/超时**无统一事实源 | 事实（README §1 + E9 生产库 325 task/178 run 的真实存在） |
| P2 | 产出文档（需求/契约/测试）**散落在各会话**，写没写全、写没写对无人把关 | 事实（E8 文档链 + E10 ReadEvidence 表真实有数据） |
| P3 | 会话式协作**不可追溯**：无法证明"谁、按什么契约、做完没" | 事实（E9 事件流 1899 条、ReadEvidence 门控存在） |
| — | 上述问题的**真实痛点强度**（是否有足够多的人愿意为此改变工作流） | **待验证**（见 §4） |

### 2.2 目标用户（分层）

| 层 | 画像 | 档位 |
|---|---|---|
| **核心（现网=1 人）** | 同时驱动 ≥2 个编码 Agent 的个人开发者 / 小团队，偏好本地、离线、零云依赖，且在意"研发过程可追溯（文档链/证据）" | 事实（当前即为该形态的单用户）+ 推断（外延画像由产品形态推得） |
| 次要 | 需要"强文档链 + 质量门 + 可追溯"的合规/审计场景团队 | 推断 |
| **明确非目标** | 只想要"并行跑 Agent 看 diff 合并"的 vibe 工作流用户；要云端多租户/团队协作的 SaaS 用户；要通用多 Agent 框架的算法团队 | 事实（与现有能力边界一致，见 §6.1） |

### 2.3 核心使用场景（按优先级）

1. **S1 · 把活派出去并看见**：建任务 → Agent 注册/领取 → 看板/拓扑/甘特看进度（事实：能力齐备，E9 活跃）。
2. **S2 · 强制"先读文档再动手"**：claim 返回必读清单 → read_document 落 ReadEvidence → submit 指纹校验（事实：422 门控代码存在，E9/E10 有数据）。
3. **S3 · 研发过程留痕可追溯**：7 段阶段 + 文档生命周期 + 事件流三者一致（事实：E8/E9）。
4. **S4 · 想法到任务的发酵**：想法→讨论→拆解→ADR（事实：能力存在；E11 标注部分"接线未用"）。

### 2.4 一句话定位（草案）

> **mio-taskhub 是一个本地单用户、零云依赖的多 Agent 任务中枢，差异不在"并行跑 Agent"，而在用服务端强制的"文档链门控 + 执行证据（ReadEvidence）"把多 Agent 协作变成可追溯、可门控、可审计的事实。**

### 3.2 差异化裁决

**（A）已被商品化、不得宣称创新的能力（事实）**

- 看板 + Agent 注册/心跳 + 领取/提交：vibe-kanban、multica、agent-orchestrator、solo、hubcode 均有。
- MCP 接入 + 本地 SQLite 持久化：`bsmi021/mcp-task-manager-server`、`djobs`、`agent-task-manager-mcp` 等大量存在。
- 任务依赖/环检测、cron/定时：常见；`taskqueue-mcp` 亦含"强制状态转移"。
- **结论**：本项目在这些点上是**平权能力**，对外宣称"创新/首创"即无证据支撑。

**（B）真正可能构成差异的**——**"组合"与"服务端强制"**（事实有能力，价值待验证）

| 差异点 | 本项目 | 最接近的同类 | 差异性质 |
|---|---|---|---|
| 文档链**生命周期门控**（进 `design` 须 `spec`+`api` **approved**，进 `planning` 须 `plan` approved，服务端拦截） | 有（E8，`LIFECYCLE_GATE`） | spec-kit 有"质量 checklist/一致性"，但为**流程模板**，非服务端硬门 | **推断**：从"约定"升级为"强制"是差异 |
| **ReadEvidence 内容指纹 = submit 前置门控**（claim 返回必读，submit 校验已读且**指纹一致**，缺失/变更即 422） | 有（E8/E9/E10） | `agent-task-manager-mcp`/`djobs` 有"证据/分级"，但不强调**服务端 422 + 内容指纹** | **推断**：机制更严，重叠度中等 |
| 文档**质量棘轮基线**（质量分/用例数**只升不降**，回退即 422） | 有（E8） | 检索未见同名机制 | **推断**：目前**未发现同类**，但样本有限 |
| 需求↔测试**追溯矩阵**（`FR-n`↔`TC-n` 覆盖校验） | 有（E8） | spec-kit 有跨文档分析 | **推断**：局部重合 |
| 22 类 kind + 7 件套链 + 合法/审批状态机的**一体化** | 有（E8） | 多为单一任务/工单模型 | **推断** |

**（C）结论（必须写清楚）**

> **事实**：本项目最有辨识度的是"**文档/证据类门控**"，而非"编排/并行/看板"。
> **推断**：把"文档门控 + ReadEvidence + 棘轮 + 追溯"整合进**一个服务端强制的本土多 Agent 中枢**，在检索到的同类中**未见完全等同的组合**。
> **待验证**：该组合是否**改变行为、降低成本、提升质量**——见 §4.3。**未验证之前，只能说"差异"，不能说"创新/更好"。**

2. **"形成价值闭环 / 数据反哺"**：E10 明确 `Evidence→新 Insight` **0/未建立**，且已被裁定不建。
3. **"生产级可靠性"**：E9 定性为"工程化 MVP → 生产候选"，首启失败 ~38%，**不是生产级**。
4. **"可扩展/多团队"**：多租户仅字段存在、无隔离测试；扩展偏代码扩展（E9）。

### 5.4 GitHub Trending

- **事实**：GitHub Trending 上榜通常要求**短期（日/周）显著 star 增量**，且需项目可被合法复用（LICENSE）、有可复现 demo。
- **推断**：以当前 1 star / 无 LICENSE / 无 Release / 无英文 README 的基线，**3 个月内登上 Trending 的概率低**；它不是"努力就能达成"的目标，而是**分发事件的副产物**。
- **待验证**：本项目内容（"服务端强制文档门控 + ReadEvidence"）是否具备传播力。
- **建议**：把 Trending 设为**观测目标而非承诺目标**，用领先指标管理：

| 领先指标 | 目标 | 说明 |
|---|---|---|
| Star 速度（周） | ≥15/周 持续 2 周 | Trending 的必要非充分条件 |
| 发布传播素材 | ≥2 篇可被转发的深度内容（如 CSDN/HN） | 由作者制造 |
| 首批外部 star 来源 | ≥3 个独立来源 | 排除熟人圈 |

**Go/No-Go**：达到"周增 ≥15 且 ≥3 独立来源"才投入 Trending 打法；否则**聚焦内部可用性**，不追榜。
