# mio-taskhub CTO级架构深度审计报告

> 审计日期：2026-09-10 | 版本：0.1.0 | 后端 7,263 行 + 测试 4,505 行

---

## 第一部分：系统定位分析

**系统定位：** 本地单用户 Agent 协调基础设施

**当前架构阶段：** 成长期（从原型到可用系统）

**目标阶段：** 稳定期（可长期维护的工具）

**架构成熟度：** Level 3/5（有正式状态机、事件系统、测试覆盖，但缺乏运维能力）

**架构与业务匹配度分析：**

当前架构对于"本地多 Agent 协调"这个业务目标是**过度设计**的。系统实现了：
- 正式状态机（21 种转换）
- Outbox 事件模式
- WebSocket 实时广播
- MCP Server 集成
- Cron 调度引擎
- 夜间运行器
- 知识图谱

这些能力对于"1-5 个 Agent 的本地协调"来说是**充足甚至过剩**的。但对于"长期可维护的工具"这个隐含目标，这种设计提供了必要的结构化保障。

**判断：** 架构复杂度略超业务需求，但考虑到长期维护性，这是合理取舍。

## 第二部分：核心架构决策审查

| 设计决策 | 收益 | 成本 | 风险 | 评价 |
|----------|------|------|------|------|
| SQLite 作为主存储 | 零运维、本地优先 | 并发受限、无网络 | 规模增长时迁移成本高 | ✅ 正确（当前阶段） |
| FastAPI + 同步端点 | 简单、线程池兼容 SQLite | 无法利用 async I/O | 高并发时性能受限 | ✅ 正确（SQLite 场景） |
| 正式状态机 | 业务规则不可绕过 | 319 行定义 + 双状态系统 | 维护两套枚举 | ⚠️ 过度（可简化） |
| Outbox 模式 | 事件一致性 | 增加复杂度 | Outbox 表可能膨胀 | ✅ 正确（最终一致性需求） |
| 4 个后台线程 | 功能完整 | 资源竞争风险 | 线程间状态同步 | ⚠️ 可合并 |
| MCP Server 代理模式 | Agent 通信标准化 | 920 行薄代理层 | 每个工具都是 HTTP 转发 | ⚠️ 过度（可自动从 OpenAPI 生成） |
| PyInstaller 打包 | 零安装分发 | 仅 Windows、构建慢 | 跨平台受限 | ⚠️ 不足（应加 Docker） |
| 无 Docker 支持 | 简单 | 部署依赖本地环境 | 环境不一致 | ❌ 不足（P1 需修复） |

### 技术驱动设计嫌疑

**`state_machine.py`** 的双状态系统（ORM 枚举 vs 状态机枚举）是典型的技术驱动设计。业务上只有 7 个状态，但系统维护了两套枚举（`TaskState` 8 值 + `State` 7 值）和一个桥接层（`transitions.py` 的 `_orm_to_status_state/stage`）。这是为了"形式化正确性"而引入的额外复杂度。

**`mcp_server.py`** 的 30 个 MCP 工具函数是 920 行的薄代理层，每个函数只是 HTTP 转发。这是为了"标准化 Agent 通信"而引入的重复代码。理想方案是从 OpenAPI spec 自动生成。

### 过度工程

**`night_runner.py`**（202 行）实现了跨午夜窗口、按日幂等生成、进程生命周期管理。对于"定时启动 Agent"这个需求，一个简单的 cron + 进程监控就足够了。

### 不足设计

**无 Docker 支持**是最明显的不足。系统只能在 Windows 本地运行，无法容器化部署。这限制了未来的扩展能力。

## 第三部分：架构风格分析

**当前架构：** 分层模块化单体 + 事件驱动组件

### 优点
- 单进程部署简单，调试方便
- 模块边界清晰（P0-P5 重构后）
- 事件驱动解耦了通知和业务逻辑

### 缺点
- 所有后台任务共享进程，一个崩溃全部停止
- SQLite 单文件限制并发和备份
- 无水平扩展能力

### 适用性
- ✅ 当前规模（1-5 agents，单用户）
- ⚠️ 未来增长（>10 agents 需要迁移）
- ✅ 团队能力（小团队可维护）
- ✅ 运维能力（本地运行无运维负担）

### 长期风险
如果用户增长到 10+ agents 或需要多用户支持，当前架构需要：
1. SQLite → PostgreSQL 迁移
2. 单进程 → 多进程/微服务
3. 本地部署 → 容器化部署

这些迁移成本在 1-2 年内不会发生，但应在架构设计中预留迁移路径。

## 第七部分：复杂度分析

## 第八部分：数据架构分析

### 数据模型

- **18 张 SQLite 表** + **1 张 JSONL 文件**（Memory）+ **Git 文件系统**（ADR）
- **CAP 选择：** CP（一致性 + 分区容忍性，牺牲可用性）
- **一致性策略：** 强一致（ORM 事务）+ 最终一致（Outbox → WebSocket）

### 数据风险

| 风险 | 等级 | 说明 |
|------|------|------|
| SQLite 单文件损坏 | P1 | 无自动备份，损坏即丢失全部数据 |
| OutboxEvent 表膨胀 | P2 | 无清理机制，长期运行后表可能膨胀到 GB 级 |
| JSONL 无索引 | P2 | Memory 查询需全表扫描，O(n) 复杂度 |
| 无数据迁移版本控制 | P3 | migrations.py 是手动维护的，无迁移历史追踪 |

### 优化方案

1. **P1：** 实施 SQLite 自动备份（每小时快照到备份目录）
2. **P2：** 添加 OutboxEvent 自动清理（保留最近 30 天）
3. **P2：** Memory 考虑迁移至 SQLite FTS5 全文搜索
4. **P3：** 引入 Alembic 迁移版本控制

## 第九部分：性能架构分析

### 完整请求链路

```
Client (React SPA)
  ↓ HTTP/WebSocket
FastAPI (sync endpoints in threadpool)
  ↓ SQLModel ORM
SQLite (WAL mode, QueuePool 5-15)
  ↓ (optional)
External: MCP Server / Git / Webhook
```

### 性能瓶颈 TOP 10

| # | 位置 | 瓶颈原因 | 影响 | 优化 |
|---|------|----------|------|------|
| 1 | SQLite WAL checkpoint | 高频写入后 WAL 文件膨胀 | 写入延迟增加 | 定期 checkpoint |
| 2 | `board.py` 聚合查询 | 每次请求执行 5+ 个 COUNT 查询 | 首页加载慢 | 缓存 5s |
| 3 | `_task_detail()` | 60 行函数执行 6 个子查询 | 单任务详情慢 | 预加载/缓存 |
| 4 | Memory JSONL 全表扫描 | 无索引，O(n) 查询 | 知识查询慢 | 迁移 SQLite FTS5 |
| 5 | WebSocket 广播同步 | `asyncio.run()` 在同步上下文 | 事件广播延迟 | 改为异步路径 |
| 6 | Cron engine 10s 轮询 | 固定间隔，无法更精细 | 任务触发延迟 | 改为事件驱动 |
| 7 | 前端 5s 轮询 | WebSocket 断开时降级为轮询 | 实时性差 | 增加重连优先级 |
| 8 | `advance_stage` 重复代码 | ~80% 与 `move_to_stage` 重复 | 维护成本高 | 提取共享逻辑 |
| 9 | 无查询缓存 | 重复查询无优化 | 相同数据重复计算 | 内存缓存 |
| 10 | 无连接池监控 | 资源泄漏不可见 | 潜在性能退化 | 添加 metrics |

## 第十四部分：架构失败预测

### 未来 6 个月

**最可能出现的问题：** SQLite WAL 文件膨胀导致写入性能下降

**触发条件：** 连续运行 30+ 天，OutboxEvent 和 Event 表积累大量数据

**症状：** 写入延迟从 ms 级增长到 s 级

**提前措施：** 实施定期 checkpoint + 数据清理

### 未来 1 年

**最大瓶颈：** `api/tasks.py` 膨胀到 1000+ 行，成为不可维护的 God Controller

**触发条件：** 新增 5+ 个任务相关端点（如批量操作、导入导出）

**症状：** 修改一个端点需要理解整个文件，回归测试成本高

**提前措施：** 拆分为 tasks_crud.py + tasks_stage.py + tasks_response.py

### 未来 3 年

**可能重构位置：** 整个后端架构

**触发条件：** 用户增长到 10+ agents 或需要多用户支持

**最大风险：** SQLite 无法满足并发需求，单进程无法水平扩展

**提前措施：** 在架构设计中预留 PostgreSQL 迁移路径

### 最可能失败点

```
最可能失败点：SQLite 并发写入瓶颈

失败原因：WAL checkpoint 不及时 + OutboxEvent 表膨胀

提前措施：定期 checkpoint + 数据清理 + 监控 WAL 文件大小
```

## 第十七部分：CTO 最终结论

### 架构最大优势
**状态机驱动的业务规则不可绕过。** 21 种显式转换 + 验证器确保了所有状态变更都经过严格校验。这是系统最核心的架构决策，也是最值得保留的设计。

### 当前最大风险
**无自动备份 + 无进程守护。** 如果 SQLite 文件损坏或主进程崩溃，全部数据丢失且无法自动恢复。这是最容易修复但后果最严重的风险。

### 最错误的三个设计
1. **双状态系统**（ORM 枚举 + 状态机枚举）—— 同一概念的两种表达，增加 50% 的维护成本
2. **`mcp_server.py` 920 行手动编写** —— 每个 MCP 工具都是 HTTP 转发样板代码，应从 OpenAPI 自动生成
3. **无 Docker 支持** —— 限制了部署灵活性和跨平台能力

### 最值得投入的三个优化方向
1. **P1：** 实施 SQLite 自动备份 + 进程守护（1 天，消除最大风险）
2. **P1：** 统一双状态系统为单一状态机（2 天，消除最大维护负担）
3. **P1：** 添加 Docker 支持（1 天，消除部署限制）

## 架构演进路线

### 0-3 个月（当前）
**解决：** 数据安全 + 部署灵活性
- SQLite 自动备份
- 进程守护（systemd/supervisord）
- Dockerfile + docker-compose.yml
- 统一双状态系统

### 3-6 个月
**建设：** 代码质量 + 可观测性
- `api/tasks.py` 拆分
- `models.py` 按聚合根拆分
- OpenTelemetry 分布式追踪
- 全局 API 限流

### 6-12 个月
**优化：** 扩展能力 + 自动化
- MCP 工具从 OpenAPI 自动生成
- 测试覆盖率提升至 80%+
- CI/CD 增加 lint + type check + coverage
- Staging 环境自动部署

### 1-3 年
**目标架构：** 如需多用户/高并发
- SQLite → PostgreSQL 迁移
- 单进程 → 多进程/微服务
- 本地部署 → 容器化部署
- 添加 API 网关 + 认证服务
