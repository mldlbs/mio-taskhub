## 背景与问题

mio-taskhub 已有六道文档链门控，但它们只约束**过程文档**，不改善 agent 写代码时的实际行为。

对真实库 `C:\Users\admin\.mio_taskhub\taskhub.db` 的 284 条 Run 实测：

| 现象 | 数量 | 占比 |
| --- | ---: | ---: |
| 执行链路故障（agent offline 85 / never started 24 / heartbeat timeout 24） | 133 | 47% |
| 真正跑过并自报结果 | 151 | 53% |

在 165 条内容型 `run.result` 中：

- 提到测试 / 构建 / lint 结果的：**87 条（53%）**
- 明确列出改了哪些文件的：**仅 22 条（13%）**

**结论：agent 自发在产出质量证据，但证据没有被收集和复用。**缺的是回流机制，不是校验。

另有两个佐证：

- `read_evidence` 已有 96 条记录、覆盖 42 个 Run，说明软性机制在本系统真实使用中会生效。
- `memory_store.py`（319 行）已实现 `add_entity` / `experience_reuse` / `search_entities`，但`memory` 表**从未创建**，是死代码。

## 目标与非目标

### 目标

- 让 agent 领取任务时**自带同类任务参考**，从而更可能写出符合项目习惯的代码与测试。
- 把已完成任务的经验沉淀为可复用资产，而非停留在单次`result` 文本里。
- 全部机制**只提供信息，不阻断任何流程**。

### 非目标

- 不给 `Run` 增加 `base_sha` / `post_sha` 强校验字段。
- 不要求 agent 必填测试命令 / 改动清单 / 版本 sha。
- 不新增任何 `422` 阻断分支。
- 不做 L3/L4 版本标识门禁（前一版审计的 A1/A2/B1 三项作废）。
- 不改造执行链路可靠性（47% 的链路故障属另一议题，本次仅记录不处理）。

## 功能需求

| 编号 | 需求 | 优先级 | 验收要点 |
| --- | --- | ---: | --- |
| FR-1 | 提供只读查询：给定 `workspace`（退化到 `project`），返回近期已完成任务的参考信息，含**测试执行方式**、**文件布局习惯**、**已知坑**三类线索；输出长度受限（单条截断 + 条数上限）；无结果返回空集合且不抛异常 | P0 | 查询接口有对应测试；无数据时返回空集合 |
| FR-2 | `claim` 返回体新增 `lessons` 字段（**增量字段**，不改既有字段语义）；无历史时为空数组且claim 正常 200；注入逻辑异常时降级为空数组，**绝不阻断 claim** | P0 | claim 响应含 `lessons`；注入异常时仍返回 200 |
| FR-3 | 任务完成时把可复用经验写入 `memory_store`；同项目后续任务 claim 时能取到；沿用既有 JSONL 存储，**不新增数据库表** | P1 | `memory_store` 的 `health()` 返回正常；后续任务可取到 |
| FR-4 | 把已完成任务的自报内容聚合成可查看指标（如「近期自报含测试证据的比例」），供人看见趋势；**不参与任何流程判定** | P2 | 指标可查询；不新增任何判定分支 |

### FR-1 详细说明：参考信息的三个来源

| 线索类型 | 数据来源 | 提取方式 |
| --- | --- | --- |
| 测试执行方式 | 历史 `run.result` 文本 | 匹配测试命令特征（如 `pytest` / `npm test` / `mvn test` / `lint` / `build` 等关键词所在句） |
| 文件布局习惯 | 历史 `files` / `deliverables` 路径 | 按目录前缀聚合，取出现频次最高的若干项 |
| 已知坑 | 失败任务的 summary / review_result | 取近期的失败记录摘要 |

### FR-2 详细说明：`lessons` 响应结构

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `test_hints` | string[] | 该项目测试怎么跑的线索，单条截断 |
| `file_layout` | string[] | 常见文件布局，单条截断 |
| `pitfalls` | string[] | 近期已知坑，单条截断 |
| `source_count` | int | 参考来源任务数，为 0 时表示无历史 |

> 无历史数据时，上述四个字段分别为空数组 / 0，**不返回 null、不报错**。

### FR-3 详细说明：经验条目结构

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `name` | string | 经验条目名，**须含项目名**（如 `mio-taskhub-测试方式`） |
| `etype` | string | 实体类型，取 `memory_store._KIND_MAP` 合法值，经验类用 `experience` |
| `observations` | string[] | 经验正文，**每条须含 project 字符串** |
| 项目归属 | — | ⚠️ `add_entity` **无 `project` 参数**（`memory_store.py:139`）；project 过滤靠 `search_entities` 在 observations 文本里做子串匹配（`memory_store.py:115-119`），故项目名必须写进 observations，否则检索不到 |

## 非功能需求

| 项 | 要求 |
| --- | --- |
| 性能 | 参考查询不引入明显延迟；`lessons` 注入后claim 响应体积增幅可控 |
| 兼容性 | 不改变既有 API 字段语义；旧客户端忽略新字段即可正常工作 |
| 可靠性 | 注入逻辑异常时降级为空数组，绝不阻断 claim |
| 可测试性 | 每项能力须有对应测试，且不新增阻断式断言 |
| 数据边界 | 只读跨任务信息，不跨 workspace 泄漏内容 |

## 约束与前提

- 本任务由 mio-taskhub 自身的文档链流程驱动，`requirement` 需`approved` 后才能进入 design。
- 验收标准另见任务 `acceptance_criteria`，其中含一条自查项：**grep 核对 `HTTPException(422` 数量不增**，用于防止实现时滑回硬约束。
