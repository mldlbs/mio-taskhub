# 技术评估报告撰写规范

> **来源**：2026-09-30 系统级评估报告经技术负责人复核，暴露 5 处"把推断写成事实"的问题。本文固化该次复核的方法论，避免重犯。
> **适用**：任何系统级评估、验收核对、可靠性报告、故障复盘。
> **核心原则**：**报告的可信度取决于"不越界"**——写多了（把推断当事实）比写少了危害更大，因为它会误导决策。

---

## 1. 铁律：证据分栏（三档）

**每一条重要结论都必须标注证据档位，不得含混。**

| 档位 | 含义 | 写法 |
|---|---|---|
| **事实** | 代码或数据**直接**证明 | "119 次 run 中 52 次 exit_code≠0" |
| **推断** | 由实现/数据推断，**无直接证明** | "120–130s 硬边界**提示**固定窗口缺陷" |
| **假设** | 目前缺证据 | "若 agent 生命周期管理有缺陷，则…" |

**禁止句式**：
- ❌ "看起来应该可以" ❌ "理论上" ❌ "大概率"

**必须区分的两组**：
- "代码支持" ≠ "真实运行证明"
- "机制被触发" ≠ "机制达到预期效果"

---

## 2. 失败率类指标：必须拆到具体原因再下结论

> **教训（本次直接踩中）**：初稿写"44% run 失败 ≈ 系统可靠性差"，被正确驳回。

**规则**：
1. **失败率不能直接等同于可靠性结论。** 必须按 `result` / `reason` 分类：`heartbeat_timeout` / `user_cancelled` / 真实异常 / 环境问题。
2. **用户主动取消不是系统缺陷**（本次 4 次 user_cancelled）。
3. **"超时"必须区分"真超时"与"窗口误判"**，且在没有存活证据前，只能写"无法区分"。
4. **先问"这是不是生命周期管理问题"**——agent 进程被杀、心跳窗口不匹配，都属此类。

**正确写法示例**：
```
事实：119 run 中 52 failed，其中 24 heartbeat_timeout。
事实：24 次超时运行时长集中于 ~120–130s（14 次落在 120.1–129.7s）。
事实：受影响任务 est_duration_min 为 30/90/120/180，窗口固定 180s 未自适应。
推断：硬边界提示存在固定时间窗缺陷（可能是 agent 生命周期管理问题）。
缺失证据：无心跳时序与 agent 存活日志 → 无法判定 agent 在 cutoff 时是否存活。
结论：先做根因定位，再决定修复方向。
```

---

## 3. 严重度分级：P0 判据必须严格

**P0 = 数据损坏 / 状态不可信 / 核心功能不可用 / 无法恢复。**
不满足以上判据的，即使"很严重"，也只能是 P1。

| 现象 | 常见误判 | 正确级别 |
|---|---|---|
| 资源浪费、垃圾任务堆积 | P0 | **P1**（方向性/浪费，不损坏数据） |
| 指标数字不好看 | P0 | **P1/P2** |
| 悬空设计（有表无数据） | P0 | **P1**（除非证明导致数据不一致） |
| 状态写入错误 / 数据丢失 | — | **P0（真）** |

**规则**：不要把所有问题都列成 P0。P0 空缺是**可接受的结论**，报告里可以写"当前无确证 P0"。

---

## 4. 不可用性断言：只能写"缺乏保证"，不能写"会失败"

> **教训（本次踩中）**：初稿写"outbox 未接入 → 事件一致性无保障 → 事件可能丢失"。

**规则**：
- 有表但无数据 = **"未使用/悬空"**，不等于"机制失效"。
- 实际在跑的替代机制要**被承认并审计**（本次：`event` 表 1429 行、20+ 类型、按天连续 → 广播机制真实运行）。
- 只能写：**"依赖 X 机制，缺乏 Y 保证"**，并说明**可恢复性是否验证过**。

**正确写法**：
> 事件一致性依赖当前提交后广播机制，**缺乏事务性保证**（广播与业务提交非原子）。是否可接受取决于广播失败的可恢复性，**尚无失败样本证明**。

---

## 5. 效果断言：要"行为改变"必须有对照数据

> **教训（本次踩中）**：初稿写"ReadEvidence 改变了 agent 行为"。

**规则**：
- "机制被触发/在运行" ← 可用计数证明（如 55 条 evidence）。
- "改善了行为质量" ← **必须有门控前后对照**：未读文档率 / 提交失败率 / evidence 覆盖率。
- 没有对照实验时，写：**"已证明能强制产生阅读证据；对行为质量的改善尚缺对照实验"**。

---

## 6. 语言分寸：技术报告避免修辞

| 避免 | 改为 |
|---|---|
| "任何新功能都是在流沙上盖楼" | "在核心状态与执行可靠性尚未建立基线之前，继续扩展会增加验证成本和噪声" |
| "系统在空转" | "存在 97 个无下游消费的自动生成任务" |
| "看板数字不可信" | "部分运行数据尚不能被完全信任" |

**理由**：修辞会削弱报告的证据属性，让读者把注意力从数据转到立场。

---

## 7. 报告的收尾格式（必备两节）

1. **附：复核与修正记录**——列出被修正的表述（原表述 / 修正后 / 依据），证明报告经过对抗性复核。
2. **压缩版核心结论**——把全文压成一句可复述的工程结论（本次："系统已产生大量运行数据，但其中一部分还不能被完全信任"）。

---

## 8. 自检清单（发布前逐条过）

- [ ] 每条重要结论都标了 **事实 / 推断 / 假设** ？
- [ ] 失败率是否**拆到了具体失败原因**？用户取消是否被排除？
- [ ] 是否把"看着严重"的东西错标成 **P0**？P0 判据是否严格？
- [ ] 是否有**"有表无数据"被写成"机制失效"**？
- [ ] 是否有**"机制运行"被写成"效果改善"**（缺对照）？
- [ ] 是否出现了"看起来应该""理论上""大概率"？
- [ ] 结论里是否区分了**"代码支持"与"真实运行证明"**？
- [ ] 是否附了**修正记录**与**压缩版结论**？
- [ ] 修辞是否收敛为中性表述？

---

## 9. 优先级排序规则

**按风险与依赖关系排序，不做"项目优劣排名"。**

- 依赖前置项优先（如"止血"必须先于"建立基线"）。
- 结构性重构**默认推迟**，除非有实验证明它是瓶颈（本次：RUoW 明确推迟）。
- **"先定位、再修复"** 优于 "先假设、就动手"（本次 heartbeat 任务改为根因优先）。
