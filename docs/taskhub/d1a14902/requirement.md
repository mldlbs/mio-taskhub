## 背景与问题

现象（2026-11-19 09:00–09:45 实测）：用户反馈「CPU 占用还是很高」。分层排查后定位到**不是** hub 本身，而是 **Tauri 窗口的 WebView2 渲染进程**。

### 分层排除过程（每一步都有实测数据）

| 步骤 | 实验 | WebView2 合计 CPU | 结论 |
|---|---|---|---|
| 0 | 起点（旧构建） | **162.6% 单核** | 远超一个核 |
| 1 | 停掉 hub（页面无数据、无卡片） | 134.9% | 与数据无关（仅 -17%）→ 是页面自身的持续开销 |
| 2 | 向已部署 CSS 注入「禁用所有动画」 | **3.2%** | 确认是 **CSS 无限动画**（-98%） |
| 3 | 仅恢复 2 个 10px 状态点的 `wsPulse` | **107.1%** | 确认「少量 box-shadow 动画」即可触发整页重绘 |

### 机制

`box-shadow` 与 `background-position` 属**逐帧重绘**属性。本机使用 `spacedeskService`（虚拟显示器）且 WebView2 无 GPU 加速 → **软件光栅化**。此时任何持续动画都会让 1280×800 **整页每帧重新光栅化**，而非只重绘动画元素。

旁证：`dwm`（桌面合成器）同时占 44%，与「每帧都在重绘整屏」一致。

### 涉及的无限定动画

| 动画 | 属性 | 使用位置 | 危害 |
|---|---|---|---|
| `wsPulse` | `box-shadow` 扩散 | `.rail__ws.is-live`、`.ws-dot.is-live`、`.np-status__dot.is-live` | **主凶**：2 个元素即 107% |
| `liveScan` | `background-position` | `.task__live`（运行中任务卡底部的 2px 扫描条） | 同类，逐帧重绘 |

### 附带发现的既有缺陷

`index.css` 的全局 `prefers-reduced-motion` 规则只设了 `animation-duration: 0.01ms`，**未设 `animation-iteration-count: 1`** → 无限动画会变成 **0.01ms 的高速死循环**。即：**用户在 Windows 开启「减少动画」不但无效，反而可能更耗 CPU**。

## 目标与非目标

### 目标（可衡量）

- G-1 无 GPU 加速环境下，Tauri 窗口 WebView2 合计 CPU **≤ 10% 单核**（起点 162.6%）。
- G-2 开启动效时，动画**不触发整页重绘**（属性改为 transform/opacity，由合成器接管）。
- G-3 用户可在**设置页**一键开关动效，选择跨重启保持。
- G-4 Windows「减少动画」开启时，**真正停止**持续动画（修复 iteration-count 缺陷）。
- G-5 **不牺牲交互手感**：悬停、面板展开、弹窗等**事件驱动**的 transition 保留。

### 非目标（明确排除）

- N-1 不做「自动检测软件渲染」：CSS/JS 侧无法可靠判定，交给用户开关更诚实。
- N-2 不删除动效代码：保留并做成开关，用户可随时开回来。
- N-3 不涉及后端接口、数据结构、任务/看板交互语义的任何改动。
- N-4 不做整站视觉改版：本次只动动画属性与开关。
- N-5 不动 `laneFlash` 等**瞬时**动画（1.3s 一次性，代价有界）。

## 功能需求

| 编号 | 需求描述 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-1 | 将「持续型」无限动画改为 **transform/opacity** 实现：`wsPulse`（box-shadow）→ 伪元素脉冲环；`liveScan`（background-position）→ transform 位移 | P0 | 视觉意图保持（呼吸光圈、扫描条）；开启动效时不触发整页重绘 |
| FR-2 | 新增应用内「设置 → 界面 → 动效」开关，选择持久化到 `localStorage`，**启动即生效**（不需等用户进设置页） | P0 | 开关可切换；重启应用后保持；刷新页面后保持 |
| FR-3 | 动效**默认关闭**（性能优先），用户可一键开启 | P0 | 首次启动即为关闭态；开启后效果正常 |
| FR-4 | 关闭动效**只停持续动画**（`animation-duration: 0.01ms` + `animation-iteration-count: 1`），**保留 transition** | P0 | 关闭后无持续动画帧产生；悬停/面板展开/弹窗过渡仍在 |
| FR-5 | 修复全局 `prefers-reduced-motion` 规则：补 `animation-iteration-count: 1 !important` | P0 | 开启系统「减少动画」后，无 0.01ms 死循环；持续动画停止 |
| FR-6 | 在无 GPU 加速环境下，Tauri 窗口 WebView2 合计 CPU **≤ 10% 单核** | P0 | 实测（同一台机器、同一窗口、40s 窗口）：162.6% → ≤ 10% |
| FR-7 | **不引入后端接口契约变更**；不新增面板；不改变任务/看板数据与交互语义 | P0 | `api` 文档如实记录「无契约变更」；既有后端用例不改断言全过 |

## 非功能需求

| 维度 | 要求 |
|---|---|
| 性能 | G-1/G-6 达标；关闭动效后不产生任何持续动画帧 |
| 兼容性 | 浏览器端 localStorage 不可用（隐私模式）时回落到默认值，不报错 |
| 可访问性 | 尊重系统「减少动画」偏好；关闭动效不影响任何功能可用性 |
| 可维护 | 动画属性与「是否持续」分离：新增持续动画必须用 transform/opacity，且必须受 `.no-anim` 规则覆盖 |
| 零副作用 | 不改后端任何代码路径；不改数据 |

## 边界与约束

- 本次改动全部落在 `web/src/`（前端资源层），后端 **0 改动**。
- 前端是 PyInstaller 的 data 资源（`_internal/web/dist`），**改前端不需重打 PyInstaller**，但需重建 `web/dist` 并拷贝到 `dist/mio-taskhub-v3/_internal/web/dist/`（Tauri 打包源）与安装版 `_internal/web/dist`。
- Tauri 窗口的 `url` 指向 `http://127.0.0.1:48620`，页面由 hub 提供 → **换前端后必须重启 Tauri 壳**才会加载新 bundle。
- `index.css` 为 CRLF 行尾、`components/SettingsView.jsx` 为 LF、`App.jsx` 为 CRLF —— 脚本改写时必须按各文件行尾保持。
- 分支命名 `task-<8 位 hex>`；push 前需 `spec`/`api`/`plan` 三份文档处于 approved。
