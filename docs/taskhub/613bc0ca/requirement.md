## 背景与问题

现状（2026-11-18 16:58–17:10 实测，非推测）：

- hub 进程 TaskHub.exe（PID 34964）13:45 启动，至 16:58 累计 2177 秒 CPU ≈ **19% 单核**；常驻内存 194MB。
- 日志（`~/.mio_taskhub/console.log`）显示前端以 5 秒为周期轮询三个重端点。最近 3000 行日志内：`/api/v1/ideas` 695 次、`/api/v1/update/status` 694 次、`/api/v1/tasks` 694 次、`/api/v1/board/summary` 550 次。
- 端点实测耗时与体积：

| 端点 | 耗时 | 响应体 |
|---|---|---|
| `GET /api/v1/tasks` | 308 ms | 988 KB |
| `GET /api/v1/tasks?cancelled=true` | 261 ms | 1.15 MB |
| `GET /api/v1/board/summary` | **1008 ms** | 2.1 KB |
| `GET /api/v1/ideas` | 17 ms | 117 KB |
| `GET /api/v1/alerts` | 8 ms | 703 B |
| `GET /api/v1/update/status` | 7 ms | 333 B |

- **单轮轮询的服务端代价 ≈ 1.6 秒**，乘以 5 秒周期 ≈ 常驻占用三分之一核。
- 根因定位到 ORM 全表加载（`api/tasks.py:298` 与 `api/board.py:254`）：
  - `select(Task).all()` 加载 2039 行**全列**（含 `labels`/`files`/`deliverables`/`doc_paths`/`doc_statuses` 五个 JSON 列）实测 **171.7 ms**；
  - 纯 SQL `group by` 聚合实测 **5.9 ms**；列投影 select 实测 **21.9 ms**（7.8×）；board 聚合版实测 **11.8 ms**（27×）。
- sqlite 埋点（`/metrics`）：81960 次 select，avg 7.36 ms、p90 11.93 ms、**max 5288.87 ms**——负载来自轮询请求本身，不是后台定时器空转。
- 数据规模：`task` 2039 行（FAILED 1506、CANCELLED 318、COMPLETED 184、QUEUED 31）、`run` 5258 行、`event` 22582 行、`taskevent` 23470 行。

**内存不是问题**：20 秒采样 WS 188.4 → 188.9 MB 平稳，线程 23–25 稳定、handles 465 无增长 → **无泄漏**，190 MB 是 Python + SQLModel + PyInstaller 基线的正常常驻。机器内存大头在 chrome 2.5 GB / idea64 2.3 GB / WorkBuddy 2.2 GB。本任务不处理内存。

## 目标与非目标

### 目标（可衡量）

> **测量口径声明（2026-11-18 实测后补）**：下文所有端点耗时目标均以**进程内 ASGI 口径**（TestClient 直打应用，不含 socket 与 uvicorn 访问日志）为准。线上 HTTP 口径含 socket 与日志写盘，绝对值更高，**两者不可混用**——原目标误用线上口径反推，已修正。

- G-1 `GET /api/v1/tasks` **≤ 120 ms**（进程内口径；改前同口径 164.8 ms）。线上口径对应 308 ms，改造后预计 ~190 ms。
- G-2 `GET /api/v1/board/summary` **≤ 120 ms**（进程内口径；改前同口径 423.8 ms，实测 101.5 ms ✅）。线上口径对应 1008 ms，预计 ~240 ms。
- G-3 单轮轮询的服务端总代价 **≤ 400 ms**（线上口径；现状 ≈1577 ms/轮）。
- G-4 hub 进程常驻 CPU **≤ 8% 单核**（现状 19%，以同等轮询负载对比）。
- G-5 **零破坏性契约变更**：响应字段名、结构、过滤语义、错误码全部不变。

### 非目标（明确排除）

- N-1 **不做列表分页**：分页会改变 `/tasks` 响应结构，波及前端全部消费方（含嵌入式视图与外部脚本），风险与收益不匹配；数据量继续增长导致再次变慢时单独立项。
- N-2 **不做内存优化**：已实证无泄漏。
- N-3 **不做日志轮转**：console.log 80 MB 无上限是独立问题，另案处理。
- N-4 **不做僵尸任务归档**：task 表 1506 条 FAILED 属数据治理议题，与本次性能根因无关，另案。
- N-5 **不改后台调度线程**：实测负载来自请求，不来自定时器。
- N-6 **不引入缓存层**：本地单用户服务，加缓存反而引入一致性风险。

## 功能需求

| 编号 | 需求描述 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-1 | `GET /api/v1/tasks` 改为**列投影**：只 select 响应实际用到的字段与过滤条件所需字段，不再加载 5 个 JSON 列 | P0 | 实测进程内口径 ≤ 120 ms（改前 164.8 ms）；响应字段名与顺序与改前一致；**响应体大小不变**（被剔除的 4 个 JSON 列本就不在响应里，体积不变正是契约的结果） |
| FR-2 | `cancelled=true` 与默认两种入参**共用同一实现**（同一份数据、同一投影）；两者是同一端点的两个入参组合，不合并为一次请求 | P0 | 带参版本 ⊇ 不带参版本（任务集合关系）；后端两个入参组合行为与改前完全一致 |
| FR-3 | `GET /api/v1/board/summary` 的阶段/状态计数改用 **SQL group by 聚合**，替代 `select(Task).all()` 全表 ORM 加载 | P0 | 实测端到端 ≤ 100 ms；各状态/阶段计数与改前逐项一致 |
| FR-4 | board 汇总**不再加载全量 Task 实体**；仅对确需对象的少数任务（待领取队列、运行中、逾期、最近完成）做定点查询，且各自带 limit | P0 | 单次请求加载的 Task 实体数 ≤ 100；计数与列表仍完整 |
| FR-5 | 前端 `board/summary` 与 `ideas` 轮询间隔从 **5 s 放宽到 30 s**；hub 已有 WebSocket `task_update` 推送承担实时性 | P1 | 轮询日志中这两类请求频次降到原来的 1/6；看板实时性由 WS 事件补齐，不影响操作体验 |
| FR-6 | 契约零破坏：响应字段名、结构、过滤语义、错误码全部保持不变 | P0 | 改前改后对同一请求做响应体字段级 diff，字段集合完全一致 |
| FR-7 | 验收以**端点实测计时**为准：同一台机器、同一份库副本、同一命令，改前改后各测 ≥ 5 次取中位数 | P0 | 前后对比表落盘 `docs/taskhub/613bc0ca/perf-compare.md`；G-1/G-2 达标（进程内口径） |
| FR-8 | 必须保持不变的既有行为：`state`/`stage`/`agent_type`/`cancelled` 过滤语义、非法入参仍返回 400 业务码、任务排序规则、字段名 | P0 | 现有针对列表端点的用例全部通过，无需改动断言 |

## 非功能需求

| 维度 | 要求 |
|---|---|
| 性能 | G-1/G-2/G-3/G-4 如上；列表端点不引入 N+1 查询，单请求 SQL 查询数 ≤ 3 |
| 可靠性 | 聚合结果与改前**逐项一致**（计数类不允许"差不多"，必须相等）；不一致视为缺陷而非优化 |
| 兼容性 | 零破坏性变更；后端两个 `tasks` 入参组合继续可用，前端合并调用后仍覆盖原语义 |
| 可观测 | 保留 sqlite 埋点；改后 `/metrics` 中 select 的 avg 与 p90 应显著下降，可作长期监控 |
| 安全 | 只读查询，不放宽任何过滤条件；`cancelled=true` 仍能取到取消态任务（该参数本就为看板展示服务） |
| 可维护 | 投影字段清单与响应字段清单一一对应，新增响应字段必须同步更新投影，避免静默丢字段 |

## 边界与约束

- 本地单用户服务，无认证；`/metrics` 有路由、`/logs` 无。
- `api/tasks.py:298` 当前是 `db.exec(q).all()` 后逐行构造 dict，投影改造只改取数方式，不改 dict 构造逻辑。
- `api/board.py:254` 当前 `db.exec(select(Task)).all()` 后调用 `_count_by_stage` 等纯 Python 辅助函数；聚合改造需保留这些函数的**输出语义**。
- 前端轮询间隔在 `web/src/App.jsx:289`（5 s）与各视图组件的 `setInterval` 中；改间隔不得影响 WS 重连计时器（`App.jsx:233` 的 250 ms tick 只更新倒计时显示，与轮询无关，不得一并改动）。
- 分支命名 `task-<8 位 hex>`；push 前需 `spec`/`api`/`plan` 三份文档处于 approved。
