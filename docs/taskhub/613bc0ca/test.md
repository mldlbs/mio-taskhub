## 测试范围

### 测什么

- **契约一致性**：改前改后响应体字段级 diff（最强断言——任何字段增删都会被抓到）。
- **过滤语义**：`state` / `stage` / `agent_type` / `cancelled` 四种组合下的返回集合。
- **聚合一致性**：`board/summary` 的 `counts` 逐项与改前相等（不是"差不多"，必须相等）。
- **性能**：端点耗时与响应体大小，改前改后同条件对比。
- **前端**：轮询频次实测下降；WS 推送仍能触发界面更新。

### 不测什么（明确排除）

- **不测并发压测**：本地单用户，不引入并发控制。
- **不测分页**：本任务不做分页。
- **不测内存**：已实证无泄漏（20 s 采样 188.4→188.9 MB 平稳）。
- **不测长时稳定性**：本地单用户工具，不做长跑。
- **不测未受影响的端点**：`/api/v1/ideas`、`/api/v1/alerts` 等契约不变，仅前端间隔调整。

### 测试环境与纪律

- **隔离库**：`MIO_TASKHUB_DB=<临时目录>/verify.db`（**必须隔离**，不碰生产库 `~/.mio_taskhub/taskhub.db`）。
- 性能对比用**生产库的只读副本**，以保证数据规模一致（2039 任务）；改前改后用**同一份副本**。
- 全量跑加 `--basetemp=<独立目录>`；并行跑用不同 `MIO_TEST_DB_PATH`。
- 失败名单落盘再读：`pytest --lf -q -rf > out.txt`。

## 验收流程

- **谁验收**：项目作者（单人项目，本人即验收人）。
- **通过条件**：TC-1 ~ TC-9 全过；契约 diff 零差异；G-1/G-2 达标；对比表落盘。
- **不通过的回退路径**：
  1. 契约 diff 非零 → **立即回退**（列投影改动不得改变响应），改用「保留实体加载 + 只改 board 聚合」的保守方案。
  2. 计数不一致 → 定位到 `_counts_from_rows` 的分组键或 `_count_by_stage` 的口径差异，逐项对齐。
  3. 性能未达标 → 检查是否漏投影字段（多余 JSON 列仍被加载）、board 是否仍有全表实体加载。
- **排查顺序**：先做 TC-2/TC-3 的契约 diff（保证没改坏）→ 再看 TC-7 计时 → 最后看服务端 sqlite 埋点（`/metrics` 中 select 的 avg/p90 是否下降）。
