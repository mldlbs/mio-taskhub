## 2. 回答源审计的"关键存疑"（Q2）

> 源审计 Q2 存疑：**`agent_offline` 的 run（progress=50）是否仍在跑，却被 agent-OFFLINE 收紧窗口误回收？**（属推断，非结论）

**本次观测证实（事实）**：

| 证据 | 值 | 含义 |
|---|---|---|
| 链路断 lag p50 | **307.4s** | 被回收时，距上次心跳已 307.4s |
| 有效超时 eff p50 | **300s** | 回收阈值 |
| **margin(lag−eff) p50** | **+8.0s** | 仅超阈值 8 秒即被回收 |
| 真死 lag p50 | 243.1s | 真死的 lag 明显更小（更接近真实卡死） |

**结论**：链路断的 run **确实在心跳窗口边界被回收**——lag p50=307.4s 刚过 300s 阈值 8 秒。
源审计的"误回收"推断**成立**：超时窗口（300s）对 inv1 系列 agent 的心跳抖动**过紧**。

> **诚实边界**：这不等于"所有链路断都是误回收"——lag p50 刚过线说明**边界性误回收占比显著**；
> 但 p95=366.8s 的部分可能确有真掉线。三分法仍成立，只是"链路断"中**边界误回收是主因**。

## 3. 已实施的修复（T3.1，承接本结论）

| 修复 | 内容 | 针对 |
|---|---|---|
| 超时上调 | `DEFAULT_TIMEOUT_SECONDS` 300 → **360s** | 覆盖 lag p50=302.8s 的心跳抖动 |
| 宽限期 | 新增 `GRACE_PERIOD_SECONDS=60`，agent 在线 + progress>0 时 base+grace | 覆盖边界性误回收（链路断主因） |
| 可读诊断 | `_task_detail.diagnostic_hint` | 失败时给用户可读原因 |

**预期效果**：360+60=420s 的窗口可将 lag≤360s 的链路断（约占 p50~p95 区间）从"误回收"转为"正常存活"。
**待验证**：修复上线后需重新观测（见 §4）。

## 5. 结论（可复述）

1. **首启稳定性已显著改善**：成功率 **86.5%**（n=239），较源审计 ~62% 提升 24.5pp，三分根因可归类。
2. **源审计"误回收"存疑被证实**：链路断 lag p50=307.4s 仅超阈值 8s 即被回收 → 超时窗口过紧。
3. **主因是 inv1 系列 agent 心跳抖动**（占链路断 253/333），属 agent 侧（项目外）。
4. **T3.1 修复已落地**（360s+60s 宽限），**效果待新样本验证**，不下终局结论。
5. **纪律**：修复后样本不足前，不得对外宣称"首启稳定"或"已达生产标准"（`03` §6.2）。
