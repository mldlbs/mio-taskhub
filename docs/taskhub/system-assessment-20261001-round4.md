## 1. 一句话结论

**工程化 MVP，**且本轮**首次出现"真实 Agent 自动消费成功"的生产实证**——但该实证**只证明闭环可打通，未证明消费率改善或价值兑现**。

依据（事实）：
- opencode CLI 首次自动消费 2 个任务，run `exit_code=0` → task `COMPLETED`；
- 洞察闭环**持续运转**（remediation 4 条，自动派生新 `[insight]`）；
- **但**：① 消费率仍 32.6%（+0.1%）；② 2 个消费的质量偏低（prompt 内容薄）；③ heartbeat 修复**仍无新样本**。

## 2. 系统真实能力

### 已真正实现（有数据/测试/真实运行证明）
- 任务状态机 + 原子认领（真实并发 E2E 零重复）；
- 文档链门控（ReadEvidence）+ 质量门 + 棘轮；
- 心跳回收 + 窗口自适应 + never_started 有界 requeue；
- 事件事务内持久化 + 尽力广播（失败注入 4 场景）；
- **洞察消费环（端到端验证）**：metric→insight→task→**真实 agent 消费→COMPLETED**；
- 空转治理：消费意愿 guard **生产生效**（10/1 执行 self-skip）；
- 安全默认收紧 + SSRF guard + claim project_scope + MCP 风险门控 + ADR XSS 修复；
- **真实 agent 执行**（opencode CLI，非 mock）。

### 部分实现
- 多 agent：**opencode 可用**（今日验证）；codex 余额不足；hermes 过慢；
- 洞察任务质量：`[insight]` 任务有 description 但**无 acceptance_criteria** → prompt 偏薄。

### 尚未证明
- **消费率改善**（32.6%，仅 +0.1%）；
- **heartbeat 修复效果**（无修复后新样本）；
- 真实长任务、跨进程、规模、多租户。

## 3. 核心价值判断

### 3.1 是否解决真实问题 / 形成闭环
```
idea(40) → 拆解 → task(298) → run(97/298=32.6%) → 完成(71)
                                    ↓ 最大断点仍是"消费率"
metrics → insight → task → **真实 agent 消费 → COMPLETED**  ← 本轮首次打通
        → 新 metric → 新 insight → 新 task（环持续运转）
```

**本轮进展（事实）**：价值闭环的**末端首次被真实打通**——不再止于"派生跟进任务"，而是"真实 agent 消费完成"。
**仍是断点**：消费率 32.6%；且消费质量薄（prompt 内容不足）。

### 3.2 AI 是否真正必要
维持三轮结论：**执行用 LLM（本轮首次实证），分析/治理用确定性**。
**本轮新增**：真实 agent 的**输出质量受 prompt 质量约束**——`[insight]` 任务无 acceptance_criteria 时，opencode 产出"消息只有占位符"的抱怨。**这是 prompt engineering 问题，非 Agent 能力问题**。

## 4. 架构评估

优点：分层可辨；状态机集中；乐观锁真实并发验证；新增安全模块职责单一。

缺陷（延续）：API 直连 ORM（59 处 db.commit）；`CANCELLED` 双语义；迁移漂移。

最大结构性风险（延续）：**消费率**（价值兑现），非并发。

扩展风险：新 agent/类型=配置级；新状态=代码级；新租户=重构。

## 7. AI / Agent 评估

### Agent 价值
**在执行**（本轮首次真实证明）：idle_worker 领任务 → opencode run → 产出 → 回写。

### LLM vs 确定性
- 继续用 LLM：agent 执行（本轮实证）；
- 确定性：洞察消费、空转治理、心跳/重试/窗口、MCP 门控；
- **新观察**：**prompt 质量是 LLM 执行效果的瓶颈**——`[insight]` 任务缺 acceptance_criteria，LLM 抱怨"无具体内容"。**改进点：自动派生任务应生成结构化、可执行的正文**（但属功能变更，冻结中，需解冻决策）。
