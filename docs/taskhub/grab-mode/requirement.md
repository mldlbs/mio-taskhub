## 1. 背景与问题

### 1.1 现状

- 任务领取有两条通道：
  - 派单：`background.py::_assign_to_idle_agents` 每 30s 把 `queued + ready` 任务分配给**在线且空闲**的 Agent。
  - 主动：`POST /tasks/claim` 供 Agent 自行领取。
- 派单通道的**触发条件是 Agent 在线**：`Agent.status == ONLINE` 且该 Agent 无在途 run。

### 1.2 实测数据：原需求前提不成立（2026-10-07 实测）

| 指标 | 值 | 含义 |
|---|---|---|
| 任务总数 | 195 | — |
| **历史 `attempt > 1` 的任务** | **0** | **195 个任务中从未发生过一次竞争** |
| **当前在线 Agent** | **0** | 派单通道的触发条件**未满足** |
| 当前执行中 Agent | 0 | — |
| ready 待领任务 | 26 | **供给过剩**，非资源稀缺 |
| `target_agent_type` 已配置 | 74 / 195 | 能力匹配机制**已存在且够用** |
| `fallback_after` 已配置 | 2 / 195 | 跨类型兜底需求极弱 |

**结论**：尚无证据证明存在「多 Agent 竞争同一任务」「抢单稀缺性」或「基于悬赏进行选择」的行为。v0.1 记录的痛点「dispatcher 派单先手占用，导致 Agent 主动领取受阻」——在**零竞争**的前提下不构成损失，而是**没有需求**。

> 方法论教训：v0.1 把该现象直接写为缺陷，**未先验证线上是否存在竞争**——用架构合理性代替需求验证。

### 1.3 真实问题

**派单通道依赖 Agent 在线，而当前 0 个 Agent 在线 → 派单线程空转，ready 池只增不减（26 个任务无人推进）。**

- Agent 是**被动等待派发**的：没有 Agent 主动询问「有什么可领」。
- dispatcher 未运行时，任务**没有任何路径**被主动发现。
- 现有 10 / 26 个 `target_agent_type` 为空的任务，存在被任意在线 Agent 拿走的错配风险（当前无在线 Agent，故尚未发生）。

## 2. 目标与非目标

### 2.1 目标

- **核心定位**：为「无人在线 / dispatcher 未运行」场景，提供一个 **Agent 主动发现并领取任务的入口**。
- 任务可标记 `grab_mode`：允许 Agent 主动领取，且**不进入**自动派单候选。
- 提供**只读**任务大厅，让 Agent 知道「有什么可领、该我做吗」。
- 主动领取**完全复用现有 `claim()`**，不新增领取路径与状态机。

### 2.2 非目标（本次明确不做）

| 不做项 | 原因 |
|---|---|
| 前端大厅 UI | 另立任务；本次只提供 API |
| 悬赏递增／匹配评分／拒单额度／失约惩罚与冷却／竞争人数统计 | **需求证据不足**（§1.2），降级为 Future（§7） |
| `GrabAttempt` 表／专用抢单并发内核／复杂 Recovery | 同上——既无竞争，独立抢单内核无使用场景 |
| 抢单经济模型 | Agent 是无状态执行器，悬赏无承载主体 |
| 扩展 `fallback_after` 复杂回退 | `2 / 195` 的使用率不支持 |
| 改动 `TaskState` / `TaskStage` 枚举 | 保持既有状态机语义 |

## 3. 用户故事 / 使用场景

- 作为 **Agent**，我想查询有哪些任务标记为可主动领取，以便在无派单的情况下**自己找到活干**。
- 作为 **Agent**，我想在领取前看到任务的目标类型与基本信息，以便判断是否匹配我的能力。
- 作为 **任务发布者**，我想让某些任务**不被自动派发**，以便由合适的 Agent 主动领取，而非被任意空闲 Agent 拿走。
- 作为 **任务发布者**，我想让未标记的任务**继续沿用现有自动派单**，以便不改变既有流程。

## 4. 功能需求

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-1 | Task 支持 `grab_mode` 布尔标记，标记该任务**是否允许 Agent 主动领取**；不引入新的抢单状态机 | P0 | 建单／改单可写入该字段；未传时默认 `false`（不改变既有任务行为）；存量任务迁移后为 `false` |
| FR-2 | 提供**只读**任务大厅接口，返回所有 `grab_mode=true` 且 `state=queued` + `stage=ready` 的任务，含 id、标题、描述摘要、`target_agent_type`、优先级、预估耗时、创建时间 | P0 | 返回体含上述字段；不含非 ready 或非 queued 任务；**不产生任何副作用**（不写库、不留痕、不加价） |
| FR-3 | Agent 可从大厅选择任务后，**复用现有 `POST /tasks/claim`**（传 `task_id`）完成领取 | P0 | 领取走既有 `claim` 路径，行为与当前完全一致；不新增领取端点、不新增中间表；成功响应与现有 `claim` 响应结构相同 |
| FR-4 | `grab_mode=true` 的任务**不进入** dispatcher 自动派单候选；`grab_mode=false` 的任务继续沿用现有派单逻辑 | P0 | `grab_mode=true` 的任务跑一轮调度 tick 后仍为 `queued`；`grab_mode=false` 任务的派单结果与改造前**逐条一致** |
| FR-5 | `target_agent_type` 继续作为领取／派单的匹配约束；为空的任务按既有规则处理 | P1 | 领取时类型不匹配的任务排序靠后（既有 `should_fallback` 逻辑不变）；本需求**不扩展** `fallback_after` 语义 |

## 5. 非功能需求

### 5.1 性能

- 大厅查询为**单次只读 SQL**，P95 ≤ 100ms（本地 SQLite，任务池 < 1000 条）。
- 默认返回 ≤ 50 条，支持 `limit` 参数（上限 200）。
- 复用现有 `claim()`，**不引入额外开销**；`grab_mode` 只是一个布尔列，参与既有候选查询的一个条件。

### 5.2 安全

- 大厅为**只读**接口，不接受任何状态变更参数。
- 领取仍走既有 `claim()` 的校验链（含 P0 修复后的 Run 所有权校验）。
- 不新增鉴权面，沿用现有 `--auth` 开关。

### 5.3 兼容 / 依赖

- `grab_mode` 缺省 `false`，**存量任务行为逐条不变**（硬约束，验收见 TC-4）。
- 不修改 `TaskState` / `TaskStage` 枚举取值与既有转移表。
- 不新增第三方依赖，不新增后台线程，不新增数据表。

## 6. 边界与约束

- **时间窗**：本次只做后端 API（3 个改动点：`grab_mode` 列 + 迁移、大厅只读接口、派单让位谓词）。
- **资源**：单人开发，无压测环境。
- **既有系统约束**：派单让位的改动必须保证 `grab_mode=false` 任务的行为**完全不变**，否则会打断现有任务推进节奏。
- **交付边界**：不触碰前端；不新增后台线程；不新增数据表。

## 7. Future（需求证据不足，当前不实现）

以下设计**已完成并通过评审**（见 [Spec v0.3](docs/taskhub/grab-mode/spec.md) 与 [接口契约](docs/taskhub/grab-mode/api.md)），但因需求证据不足**暂缓实现**：

| Future 项 | 证伪依据 |
|---|---|
| 悬赏递增 | 无竞争即无「待价而沽」行为；Agent 无收益感知 |
| 匹配评分 | `target_agent_type` 已覆盖 74/195，够用 |
| 拒单额度 | `2/195` 的 `fallback_after` 使用率不支持「拒单」概念 |
| 失约惩罚／冷却 | 零竞争下无从触发 |
| 竞争人数统计 | `attempt > 1` 为 0，统计恒为 0 |
| `GrabAttempt` 表 | 无竞争即无留痕需求 |
| 专用抢单并发内核 | 复用 `claim()` 的 CAS 已足够 |
| 复杂 Recovery | 复用既有 reaper 语义即可 |
| 抢单经济模型 | Agent 是无状态执行器，悬赏无承载主体 |

**重新启用的触发条件（可观测）**：满足任一即重新评估——

1. `attempt > 1` 的任务数持续 > 0；
2. 存在 ≥ 2 个 Agent 同时竞争同一任务；
3. ready 池长期 > 在线 Agent 数 × 3。
