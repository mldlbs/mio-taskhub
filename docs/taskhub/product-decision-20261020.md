# mio-taskhub 收窄决策 v1.0

> 日期：2026-10-20 ｜ 决策人：作者（单人项目）
> 依据：`product-evaluation-20261020.md`（产品级评估）+ 本轮设计讨论
> 一句话：**这个项目没有"发展空间"问题，有"过度建设"问题。本决策做减法——保留一个能拦假完成的最小质量门，其余全部冻结。**

---

## 0. 总原则（先立规矩，再谈条目）

- **会在"相当一部分合法完成"上触发的检查，只能"警告/标注"；只在"明确的失败或撒谎"上触发的检查，才配"拦截"。**
- 硬证据：系统已有 `force=true` 绕过 + `doc_gate_exempt` 迁移把存量任务全置豁免 → **门禁一严就被关掉**。被绕过的门禁是演戏，不是门禁。
- 冻结 ≠ 删代码。冻结 = 停止投入、停止调度、停止当价值宣称、移出主链路；代码留着，解冻有据。

---

## 1. 唯一保留/投入项：窄门禁（拦"假完成"）

**做什么**：在 `submit_result` 成功路径（大致位置 `api/runs.py` 成功分支，待实现时核对）上——

- 采集：`Run` 落一个 `diff_summary`（改动文件数 / 增删行数 / 涉及路径列表），**不存全文 diff**。
- 拦截判据（唯一一条）：`success=true` **且** 任务属代码类 **且** `diff_summary.files_changed == 0` → **422**。
- 豁免：纯文档/决策类任务（requirement / plan / design 等无代码产出的 kind）不要求 diff。
- 降级为标注（**采集但不拦**）：测试是否通过、diff 改动质量 → 渲染进任务详情「完成报告」每次执行旁的一行提示（warn 色调），并写入「动态」tab；**不进 ReviewPanel 自动预填**（该清单人手勾，避免过度建设）。

**为什么只此一件**：它是唯一能把"完成"从"Agent 自报"变成"有硬证据"的改动；便宜（一条 git 命令）、几乎不误伤真正干完的活（真做完必有改动）、信号明确。正常完成的 diff 非空，门根本不响——所以"拦得住假完成，堵不住真推进"。

### 1.1 界面落点规范（产品级）

| 落点 | 呈现 | 职责 | 改动位置 |
|---|---|---|---|
| 右上角 toast | 红底 + 左侧红条 + 「已拦截」chip | **打断**：立即通知 | `App.jsx:164` 事件表加 `run.result_rejected` |
| 完成报告 · 拦截卡片 | 红框卡片 + 红色「已拦截」chip + 原因 + 下一步 | **存档**：为什么被拒 | `TaskDetail.jsx:376-395` |
| 动态时间线 · 事件行 | 红底事件行 + 「结果被拒」chip | **审计**：发生过什么 | `TaskDetail.jsx:593` event-timeline |
| 完成报告 · 标注行 | 琥珀底左条 + 「提示」chip | **常驻提示：不弹 toast** | `TaskDetail.jsx:380-390` exit_code 旁 |

**关键设计决策**
1. **拦截要打断，标注不打断** → 只有**拦截**弹 toast（红）；**标注绝不弹 toast**（否则每跑一次闪一次，噪声淹没信息），只在「完成报告」常驻一行。
2. **拦截 ≠ 失败 ≠ 取消**，三者在时间线上必须视觉可分：拦截用红色 chip「已拦截」且**任务不进入完成**；失败 = run 自身失败；取消 = 人为/自动作废。混用会进一步污染成功率口径（见 §4 P1-1）。
3. **不新建面板**：全部复用 TaskDetail 这个已在用的抽屉。

**文案规范（三段式：发生了什么 / 为什么 / 下一步）**
- 拦截：`拒绝提交：声明 success=true，但 git diff 为空（0 文件 / 0 行）` + `下一步：实际改动后重试；本次执行不计入完成`
- **禁止套用通用 422 文案**（`api.js:11` 现为"数据校验失败，请检查必填项"）→ 本门禁需**独立错误码**，前端按码渲染专用文案。
- 标注：`提示　未检测到测试执行 · 不影响放行`（必须写明"不影响放行"，否则用户会误以为被拦了）

**无障碍**：不得只靠颜色区分，必须带文字标签（已拦截 / 提示）；toast 需 `aria-live`。

**明确不做（防过度建设）**：不新建面板；不给标注弹 toast；不自动预填 ReviewPanel 清单（人手审阅）；不把 diff 全文塞 UI（只放文件数 / 行数）。

**可见性缺口（今天确实看不见，需补接线）**：被拦的 submit 走 `POST /runs/{id}/result`，UI 无该动作入口（纯 agent/CLI），且无 `result_rejected` 事件 → 人**看不见**被拦；完成报告现只有 exit_code，无标注位。

**命名坑**：`GateStatusCard` 的"生产闸门"是创意 idea 闸门，与任务质量门无关，别混。

**验收标准**：
1. 造一个"声称 success 但零改动"的 Run → 必须 422。
2. 一个真实有改动的 Run → 必须正常放行（无误伤）。
3. 文档/决策类任务 → 不因无 diff 被拦。
4. 成功后能指着一例："它拦下了一次我本会放过的假完成"——这是本条的唯一成功判据。
5. 被拦的 submit 在人的界面可见（动态 tab 有 rejected 记录 + 红色 toast）；标注在 完成报告可见（提示行）。

**停止/回退条件**：上线后若开始频繁误伤合法完成（说明任务分类没分清）→ 立刻回退为"仅标注"，**不要加严**。宁可门是哑的，不能门是堵的。

## 2. 拦 vs 标注 矩阵

| 检查 | 成本 | 合法工作时会误触发？ | 信号 | 处置 |
|---|---|---|---|---|
| 声称 success 但 diff 为空 | 一次 git 调用 | 几乎不会 | 明确的假完成 | **拦截（422）** |
| 测试是否通过 | 高（要跑） | 会（在途/无测试工作大量存在） | 模糊 | **标注→完成报告提示行，不拦** |
| diff 改动质量 | 高 | 会 | 模糊 | **标注→完成报告提示行，不拦** |
| 文档读证指纹 | 已有 | 低 | 较明确 | 维持现有门禁 |

## 3. 冻结清单（停止投入 + 停止宣称价值，代码不删）

| 项 | 处置 | 理由（证据） | 解冻条件 |
|---|---|---|---|
| creativity 调度（webhook / idea-generate） | 冻结（已停） | 假设 61 行全空、可验证增量≈0 | 有新的价值假设 + 对照证据 |
| observer 机会发现（taskhub 侧） | 冻结 | 素材噪声、洞察错配、有效产出≈0 | 上游素材质量改善有据 |
| Prometheus / SLO / tracing | 冻结 | 单用户本地工具，无人看指标 | 出现第二个真实用户 |
| memory gateway | 冻结 | 无省时证据 | 作者能说清省了什么具体时间 |
| ADR 投影 | 冻结 | 同上 | 同上 |
| idea 子系统扩张 | 冻结 | 53 条仅 1 采纳、无交付追踪 | 有真实使用 |
| 超出结构校验的文档质量阈值 | 冻结 / 降宣称 | lint 仅结构校验，内容正确性未知 | 补内容校验能力 |
| 多入口（advance/move、create/create_from_template） | 合并收敛 | 冗余，增加维护与理解成本 | — |

> 注：creativity / observer 的**引擎本体属上游 mio agent runtime**，不在本仓删除范围；本仓冻结的是"把它当 taskhub 核心价值闭环去调度与宣称"。

| 编号 | 事项 | 为什么先做 | 验收 |
|---|---|---|---|

## 5. 反证 / 复审条件（什么情况下本决策要改）

1. 窄门禁频繁误伤合法完成 → 说明判据或任务分类错了，回退为"仅标注"（见 §1 停止条件）。
2. 作者能演示某个冻结项真的省了具体时间 → 对应条目解冻，本决策按证据修订。
3. 诚实记账后发现 96.5% 运行失败主要是口径失真而非真实故障 → 可靠性判断上修，"先修可靠性"的紧迫性下降。
4. 出现第二个真实用户 → 重新评估 SLO/tracing 等"多用户才成立"的冻结项。

---

## 6. 执行顺序（单人，按序推进，不并行铺开）

1. **止血**：P1-1 口径、P1-2 自审（地基）。
2. **上窄门禁**：diff_summary 采集 + 空 diff 拦截 + 三类豁免 + §1.1 界面落点（唯一保留项）。
   → 可实施方案见 `narrow-gate-implementation-plan-20261020.md`（含判据定义、后端 B1–B8 / 前端 F1–F7、三个必踩的坑、分批验收）
3. **冻结**：按 §3 停掉调度、移出主链路、改掉价值宣称。
4. **观察一个真实周期**：用 §1 验收第 4 条判断成败，再决定要不要动别的。

> 时间表：单人项目，建议每步一个专注周期，具体排期由作者定；本决策只定顺序与验收，不排日历。
