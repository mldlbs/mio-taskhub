## 1. 一句话结论

**mio-taskhub 是一个"真实可用但被严重高估"的本地单用户跨 Agent 研发任务枢纽：其唯一被实证的价值是"服务端强制的先读文档再写码 + 文档/证据门控"，让一名开发者驱动多个编码 Agent 时研发过程可追溯；但被当作"核心价值闭环"去推广的"自主创意/洞察价值发现"已实证失败（可验证增量≈0、taskhub 侧调度全部停摆——注：生成/采集引擎本体属上游 mio agent runtime，taskhub 侧只是挂调度消费并把它包装成核心卖点，后者才是值得质疑的产品判断），且全系统 96.5% 的运行失败率与 86.7% 的任务取消率暴露了可靠性与指标口径的真实风险。最关键的约束是：产品把"流程闭环"当成了"价值闭环"。**

## 3. 核心用户与价值判断

**目标用户【事实】**：同时驱动 ≥2 个编码 Agent（opencode / claude code / codex / hermes / WorkBuddy）的**个人开发者或小团队**，偏好本地、离线、零云依赖、在意研发过程可追溯（定位文档 `roadmap/01-positioning.md:84`）。

**真实使用证据【事实】**：现网实际只有 1 人（作者自述"核心 现网=1 人"，`roadmap/01-positioning.md:84`），无外部真实使用者（社区基线 G5=0）。179 条 COMPLETED 任务标题均为具体工程交付（如「【需求23-F5a】前端 useFacilityMap 染色」「后端 getWorkflowRequest 透传端点」），横跨 csps-app-service、agent-dev、mio-taskhub 等真实项目——**说明产品对作者本人确有真实用途**。

**替代方案【事实+推断】**：无门禁的多 Agent 并行（各 Agent 自带会话）、Jira/Linear（云端、非本地、不强制文档门禁）、纯脚本/README 约定。mio-taskhub 的差异化是"把先写文档再写码由口号变成服务端强制墙"，而非看板/注册/持久化（这些已被定位文档明确列为"商品化平权能力"，不得宣称首创）。

**需求真实度分级**：
- 【事实】"多 Agent 并发时谁在干什么、干到哪了、产出靠不靠谱"是真实痛点，且作者本人已用 179 个完成任务证明需求成立。
- 【假设】"门禁提升产出质量""价值闭环自喂养""生产级可靠性"——定位文档自身已声明**缺乏证据、不得对外宣称**（`roadmap/01-positioning.md:167-174`）。
- 【未知】外部用户是否真有此需求（现网仅 1 人）。

**定位偏差【推断】**：产品把自己包装得比实际更"生产级/智能化"，但核心价值是**确定性的流程强制**，不是 AI。把大量工程资源押在"自主创意发现"（AI 生成）上，偏离了已被验证的真实需求（多 Agent 研发可追溯）。

## 4. 核心业务闭环审计

识别 2 条端到端链路，分别审计：

### 链路 A：开发任务闭环（被验证的部分）
`需求产生 → 任务创建 → Agent 认领(claim) → 执行(run) → 提交结果(submit_result) → 文档/证据门控 → 完成(completed) → 业务交付`

- **真实输入/输出【事实】**：179 条 COMPLETED 任务对应真实工程交付，跨多个真实项目。
- **失败可发现性【事实+推断】**：异常严重——5170 次运行中 exit=1（失败）4984 次（**96.5%**），exit=0 仅 183 次；1928 任务中 CANCELLED 1676（86.7%），其中 1571 条带 `failed_at`。即绝大多数运行以失败告终，且失败被大量"自动清理为 cancelled"。API `/api/v1/tasks` 仅返回 252 条（179+38+35），**恰好是剔除 1676 条取消后的"表面健康"子集**——存在指标粉饰风险。
- **是否需要大量人工补救【未知→偏肯定】**：96.5% 运行失败率意味着要么系统极不可靠，要么"失败"语义被滥用（如超时被记失败、重试不计成功）。无论哪种，都说明闭环的**成功路径是少数派**，真实用户体验存疑。
- **价值证明【推断】**：179 个完成任务确实有交付，但 DB 无"消费方/收益"字段，**completed ≠ 有价值**，无指标佐证收益。

> 判定：链路 A 存在**流程闭环 + 部分技术闭环**，但**业务价值闭环未被证明**（成功率极低 + 无收益度量）。若 96.5% 失败率是真实可靠性问题，则核心链路本身脆弱；若是口径失真，则指标不可信。必须二选一澄清（见 §7 P1-1）。

### 链路 B：创意/洞察价值发现闭环（已失败的部分）
`素材采集(observer) → 洞察配对 → LLM 生成创意 → 评分/采纳 → 转化为任务/机会`

- **真实输出【事实】**：`creativity-hypotheses.jsonl` **61 行全部为空**；`creativity-combos.jsonl` 61 行但源名暴露测试/模板残留（S1–S6、alpha/beta），且 20 条带 `observer-insight` 源内容自我证伪（标【GitHub】实为 B 站/抖音热榜）。
- **自动化状态【事实】**：3 个调度任务 `enabled` 全部为 0（已禁用）；每日创意 webhook（job 1271eac5）最后状态 ERROR（"creativity 连续两次返回空"）；idea-generate 最后运行停在 2026-09-27。
- **价值结论【事实】**：作者自有材料（`R292 验收材料`、`素材源核验报告-20261008.md`、`creativity-strategy-degrade-issue.md`）明确："产出全是缺失/空集变体、可验证增量≈0""素材多为资讯噪声，不能直接当机会"。

> 判定：链路 B **已断、价值验证失败**。这是"有流程记录、无业务收益"的典型。

## 6. 架构、数据、AI 与安全评估

### 6.1 架构【事实为主】
- **优点**：核心状态机严谨（`state_machine.py` LEGAL_COMBOS + T1–T24 + actor 鉴权），分层清晰（api / workflow / models）。文档生命周期门控修复后逻辑正确（累计式 `_gates_upto`、文件落盘才放行）。
- **冗余【事实】**：阶段推进有 `advance_stage` 与 `move_to_stage` 两个端点；任务创建有 `create_task` 与 `create_task_from_template`；另有一套平行 idea 子系统自带评审，与 Task 评审并存。属"渠道并存"，但增加维护与理解成本。
- **领域模型缺口【事实】**：`Run` 无 `changed_files`/`diff` 字段，`GitRef` 仅存分支引用——领域层根本不表达"实际改了什么"。

### 6.2 数据真实性【事实+推断】
- **数据存在且可信（一致性）**：DB、API、creativity store 数字互相印证；observer 目录 mtime 连续无造假。
- **数据证明价值？【推断·否定】**：数据反而证明创意子系统 96.5% 运行失败、假设全空、自动化停摆。
- **口径风险【事实】**：`cancelled` 与 `failed` 语义混淆（1571 带 failed_at 却标 cancelled），API 默认屏蔽取消项制造"健康子集"——**统计口径不一致**，直接削弱所有"成功率/成熟度"声明。

### 6.3 AI 必要性【推断为主】
- **真正用到的 AI**：仅 creativity 生成（LLM 配对+润色）。其余（doc lint、observer 采集、门控）均为确定性代码。
- **AI 是否降本增效【事实·否定】**：creativity 经对照材料确认"可验证增量≈0"，且免费上游模型随机空回/400，稳定性差。无对照实验，不得宣称效率提升。
- **错误传播【推断】**：自审缺口 + submit_result 直接采信 Agent 自报 `success:bool`（`reviews.py`/`runs.py` 成功路径仅校验所有权+状态+读证版本）→ AI/ Agent 自报成功即放行，错误可直达"完成"。

### 6.4 安全与权限【事实】
- **自审绕过【事实】**：`reviewer` 为自由字符串；自审校验仅当 `reviewer` 非空触发（`reviews.py:86`）；传空 reviewer 或 `self_review=true` 仍可自审通过 → 评审信任链可被同一 Agent 自破。
- **无越权直接路径【事实】**：`assert_run_owner` 所有权校验存在，写操作黄金顺序（404→所有权→状态）基本成立。
- **原子性/幂等【事实】**：迟到结果纠正（T22）已处理 `run finished` 后提交；重复提交判据为 `exit_code==0 且 state==COMPLETED`。
- **敏感数据【未知】**：未逐一核查注入/权限扩大面，但核心写操作有所有权边界。

### 6.5 界面可见性【事实】
- **拦截对人是不可见的**：`submit_result`（`POST /runs/{id}/result`）无 UI 入口（纯 agent/CLI），且无 `result_rejected` 事件；toast 只认 `stage_advanced / cancelled / completed / failed` 等固定事件（`App.jsx:164`）。
- **标注无承载位**：TaskDetail「完成报告」只显示 exit_code 与自报 result（`TaskDetail.jsx:376-395`）；「动态」tab 有执行历史+状态变更两块（`:580-622`），但没有"标注"语义。
- **ReviewPanel 不自动带出 run 信号**：检查清单为人工勾选（`ReviewPanel.jsx:6-13,133-143`）。
- 落地规范见 `product-decision-20261020.md` §1.1。

## 7. 问题清单（按 P0–P3）

### P1（核心价值/重大可靠性/授权缺陷）
- **P1-1 成功率/失败率失真【事实】**
  - 证据：5170 运行 exit=1 占 96.5%；1928 任务 CANCELLED 86.7%（1571 带 failed_at）；API 仅返回剔除取消后的 252 条。
  - 影响：无法判断系统真实可靠性；所有"成熟度/首启成功率"声明失效。
  - 触发：任何长任务 / 超时 / 重试场景。
  - 根因：失败语义滥用 + 失败自动清理为 cancelled + API 默认过滤。
  - 措施：区分"主动取消/失败清理/真实失败"；停止把失败计入 cancelled；暴露真实成功率指标。
  - 验收：DB 中 cancelled/failed 语义清晰可查，API 提供含失败的全量统计。

- **P1-2 评审自审绕过【事实】**
  - 证据：`reviewer` 自由字符串；`self_review=true` 或空 reviewer 可自审通过（`reviews.py:86`）。
  - 影响：门控信任链可被同一 Agent 自破，"approved" 不可信。
  - 措施：取消 `self_review` 绕过通道；reviewer 须为与最近执行者不同的标识；明确 scope 禁用空 reviewer。
  - 验收：同一 agent 自审被 409 拒绝（无绕过通道）。

- **P1-3 验收空心化【事实】**
  - 证据：无变更识别（无 git diff）、无测试执行器（test 仅文档 kind）、submit_result 采信 Agent 自报 success。
  - 影响：宣称"提升产出质量"无依据；"完成"不代表"做对/测过"。
  - 措施：要么补齐 Run↔代码变更绑定 + 真实测试执行，要么停止"质量提升"宣称。
  - 验收：完成态任务可追溯到具体代码改动与测试结果，或对外口径降为"过程可追溯"。

### P2（体验/维护性/完整性）
- **P2-1 创意/洞察闭环应正式停止【事实】**：已暂停但代码/调度仍在；建议删除或隔离，回收两个调度任务资源。验收：调度任务移除或明确归档，无残留空转。
- **P2-2 多入口冗余【事实】**：advance/move、create/create_from_template、idea 平行评审。验收：收敛为单一主入口或明确文档区分。
- **P2-3 observer 双数据目录歧义【未知】**：agent-dev 根与 mio-taskhub 子目录各一份，不明确哪份被消费。验收：明确唯一数据源。
- **P2-4 文档严重失真【事实】**：README（119/40/641、v0.6.0）与 roadmap（325 任务/178 运行）与实测（1928/5170）漂移。验收：从代码派生 README/roadmap 数字。

### P3（优化/未来）
- **P3-1** 文档质量 lint 仅结构校验，内容正确性未知——降预期，不宣称质量。
- **P3-2** idea 表 53 行仅 1 采纳、无交付追踪——明确该子系统定位或合并。
- **P3-3** 缺乏端到端/真实环境对照实验——补最小实验设计（见 §9）。

## 10. 最终产品裁定

- **产品是否值得继续投入？** **值得，但必须收窄。** 其"服务端强制文档/证据门控 + 多 Agent 研发可追溯"对单人多 Agent 开发者有真实、被 179 个完成任务佐证的价值。但当前投入结构严重错位——把最多资源放在已证伪的自主创意闭环上。

- **当前最核心的产品价值是什么？** **确定性的流程强制（先读后写 + 文档/证据门控）带来的研发过程可追溯性**，不是 AI、不是编排、不是看板。这一点要写进定位并对外如实表述。

- **最大的产品设计错误是什么？（2026-10-20 复核修订）** 经复核，原"在自主创意闭环上押注是设计错误"的归因**不准确，予以收回**：creativity 生成引擎属**上游 mio agent runtime（mio-intelligence）基础设施**，并非 mio-taskhub 的设计；其"机制验证成功、价值验证失败、已暂停"是**被 disciplined 叫停的实验结论**（验证了通用配对/评估/润色能力，只是 idea-generation 产品闭环不成立），不属于设计错误。**真正由 mio-taskhub 自身承担的最大设计缺陷是**：**把"失败"静默清洗为"取消"、并用 API 默认过滤制造表面健康度（P1-1）**——这直接破坏产品自诩的"证据驱动"立身之本。次一级的产品判断失误是：把一项**未经验证的上游能力**当作 taskhub 的"核心价值闭环"去推广与宣称，导致文档/定位口径跑在证据前面。

- **哪些功能应该停止建设？** 不是"删除创意/采集引擎"（它们属上游基础设施且机制已验证），而是：**停止将 creativity / observer 作为 taskhub 的核心价值闭环去调度与宣称**（冻结 taskhub 侧两个调度任务与相关价值话术）；idea 子系统扩张、超出结构校验的文档质量阈值、可观测性/SLO 等锦上添花项暂缓，直到核心可靠性与价值被证明。

- **哪项证据最可能推翻当前判断？** 若 96.5% 运行失败率主要是"超时被记失败/重试不计成功"等口径失真而非真实故障，则**核心链路可靠性结论需上修**；反之若为真故障，则核心闭环本身脆弱，连"看板"价值都受质疑。需在干净运行中做诚实的成功/失败记账来定夺。

- **下一阶段最重要的唯一目标？** **用一次干净、可观测、含真实成功/失败记账的 30 任务试点，证明核心闭环的可靠性与"门控是否真降返工"**；在此之前，停止一切新功能建设，只做口径修正与自审收敛。
