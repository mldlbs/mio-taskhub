# 抢单模式需求裁剪裁定（2026-10-07）

## 背景
原需求提出「学美团/滴滴做抢单模式」，并据此产出 Spec v0.3（21节全填、质量分 100）。
评审通过后用户要求重新验证需求真伪，实测数据推翻了原需求前提。

## 证伪依据（生产数据，2026-10-07 实测）
| 指标 | 值 | 含义 |
|---|---|---|
| 任务总数 | 195 | — |
| 历史 attempt > 1 的任务 | **0** | 195 个任务中**从未发生过一次竞争** |
| 当前在线 Agent | **0** | dispatcher 启动条件未满足 |
| 当前执行中 Agent | **0** | — |
| ready 待领任务 | 26 | 供给过剩而非稀缺 |
| target_agent_type 已配置 | 74 / 195 | 能力匹配机制**已存在** |
| fallback_after 已配置 | 2 / 195 | 跨类型兜底需求极弱 |

结论：**尚无证据证明存在多 Agent 竞争同一任务、抢单稀缺性、或基于悬赏进行选择的行为。**

## 三重伪需求论证
1. 抢单机制的前提是资源稀缺（订单多、骑手少），实测为**供给过剩**（26 待领 / 0 执行）
2. 原文档把「dispatcher 派单先手占用」记为缺陷，实为合理设计——既无 Agent 竞争，「抢不到」不是损失而是**没有需求**
3. 悬赏的经济学前提是「劳动者有选择权且追求收益最大化」，而 Agent 是**无状态执行器**，只会执行返回的第一条 → 悬赏**无承载主体**

## 裁定
- **需求核心重新定位**：不是「抢单系统」，而是
  > 为当前无人在线 / dispatcher 未运行的场景，提供一个 Agent 主动发现并领取任务的入口。
- FR 从 12 条收敛为 **5 条**（见 requirement.md v0.2）
- Spec v0.3 标记为「**设计完成、暂缓实现（需求证据不足）**」，正文保留不删
  —— 保留价值：一旦真出现多 Agent 竞争，设计可直接启用；且评审过程本身是有效的设计训练

## 被降级为 Future 的设计（需求证据不足，非不做）
悬赏递增 / 匹配评分 / 拒单额度 / 失约惩罚与冷却 / 竞争人数统计 / GrabAttempt 表 / 专用抢单并发内核 / 复杂 Recovery / 抢单经济模型

## 重新启用的触发条件（可观测）
满足任一即重新评估：
-  的任务数持续 > 0
- 存在 ≥ 2 个 Agent 同时竞争同一任务
- ready 池长期 > 待领Agent 数 × N（N ≥ 3）

## 方法论教训
第一轮把「派单截胡」当痛点写入需求 §1.2，**未先查线上是否存在竞争**——用架构合理性代替需求验证。
需求文档的质量分（100）只证明结构完整与追溯无缺口，**不证明功能存在、需求成立**。
