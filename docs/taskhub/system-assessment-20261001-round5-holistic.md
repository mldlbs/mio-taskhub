## 1. 一句话结论

**工程化 MVP（偏生产候选），是一个"机制丰富、真实可用、但多条链路使用率不均衡"的系统。**

依据（事实）：
- **真实使用**的链路：任务流转、文档链（45 task 挂文档/33 evidence）、想法拆解（36/41）、讨论（48/53 有结论）、可观测快照（SLO 2016/依赖 20109）、定时任务（111 次执行）、**真实 agent 消费（openclose，本轮已证）**；
- **建了但几乎没用**的链路：自定义告警规则（alertrule=0）、plan 表=0、taskreview=0、appconfig=0、ideauserpref=0；
- 前几轮**过度聚焦**的"消费率 32.6%"——是**一个**指标，与"文档链使用率""告警规则空置""多视图冷热"并列，**不是系统的全部**。

## 3. 核心价值判断（回到"价值是什么"）

### 3.1 解决什么问题
**多 AI agent 协作的"编排 + 证据 + 想法孵化"中枢**。一句话：
> 让多个 CLI agent（opencode/codex/hermes）在一套**任务状态机 + 文档证据门控 + 想法漏斗**下协作，产出可追溯。

### 3.2 价值构成（不是单一指标）
| 价值维度 | 真实使用证据 | 评价 |
|---|---|---|
| 任务编排 | 298 task / 137 run / 真实并发认领 | **成立** |
| 证据留痕（ReadEvidence） | 33 evidence、45 task 挂文档 | **成立（差异化）** |
| 想法漏斗 | 41 idea→36 拆解→53 讨论 | **成立** |
| 洞察→行动闭环 | 7 insight→派生 task→真实消费 | **本轮打通** |
| 可观测 | SLO/依赖快照持续采集 | **成立但少消费** |
| 自更新 | 完整链路 | **成立** |
| 定时/空闲计划 | 111 执行 + guard | **成立** |

### 3.3 AI 是否必要
- **执行**：LLM 不可替代（本轮真实实证）；
- **治理/分析**：已确定性化（洞察消费、空转 guard、心跳、门控）；
- **prompt 质量**是 LLM 执行效果的瓶颈（R4 发现）。

## 4. 架构评估（全系统）

**分层**：`api(5906) → workflow/models/db → observability/scheduling/update/ops`，边界大体清晰；前端 20 视图集中于 App.jsx 路由。

**模块耦合**：
- 优点：状态机集中（workflow）、事件统一（events.py）、文档链独立（doc_chain/doc_quality/doc_lifecycle）；
- 缺陷：API 层直连 ORM（59 处 db.commit，RUoW 留档）；`models.py` 486 行承载 30+ 实体（单文件偏重）。

**最大结构性风险（全系统重判）**：
> **不是并发、也不只是消费率，而是"多条链路各建一套，但缺乏统一的消费/反馈闭环"**——表现：
> - 告警规则建了不填（alertrule=0）；
> - 计划表建了不用（plan=0）；
> - 洞察算了但仅最近才接消费；
> - SLO/依赖快照海量采集（20109）但无下游消费。
> 即 **"计算闭环多、价值闭环少"** 是系统性特征，不限于任务消费。

**扩展风险**：新 agent/类型=配置级；新状态=代码级；新租户=重构。

## 附：前几轮偏差的自我纠正（技术负责人指正）

**R3/R4 的收缩**：把"消费率 32.6%"当作头号并顺着"空闲计划"深挖，**偏离整体评估**。
**纠正**：本轮恢复全系统视角——32 表/7 子系统/20 视图并列评估；消费率**降级为"之一"**；新增并前置 **P1-A 系统性"建而不用"**（alertrule/plan/taskreview 空置 + SLO 海量采集无消费），这比单一消费率更能反映系统实际成熟度。
**方法论**：评估必须**防"指标绑架"**——一个醒目的坏指标容易吸走全部注意力；应按"子系统 × 使用度 × 证据"矩阵均衡取样（本轮已补）。
