---

## 0. 核心结论

> **当前瓶颈已从"任务协议正确性"转移到"Agent 生命周期可靠性"。**
> 首次调度成功率不足，**系统通过 requeue 重试掩盖了调度层的不稳定**——不是"执行不可靠"（最终 16/16），而是**"首次调度不稳定、靠自愈兜底"**。

---

## 1. 两类失败的定义（代码事实）

| 类别 | 判定条件（代码） | progress 特征 |
|---|---|---|
| `never_started` | `progress == 0`（claim 后**从未心跳**） | 0（+ 偶发 100） |
| `agent_offline` | `agent is None or agent.status == OFFLINE`（回收时 agent 已离线） | 0/20/50/55/65/70/100 |

**cohort 内失败尝试（n=16）**：10 次 = `never_started 5` + `agent_offline 5`。

---

## 2. 四问回答

### Q1：`never_started` 与 `agent_offline` 是否同一根因？
**部分同源，但触发点不同（事实）**：
- **共同根因**：都是 **agent 进程未及时/未持续运行**（opencode 会话启动失败或中途掉线）；
- **区别**：
  - `never_started` = **claim 后 agent 从未心跳**（进程没起来）；
  - `agent_offline` = agent **曾经心跳过**（progress 20~70），但回收时已被标 OFFLINE（进程中途死/掉线）。
- **证据**：cohort 中 `agent_offline` 的 progress ∈ {50}（肚子刚起就掉），`never_started` 的 progress=0。
- **结论**：**同一根因族**（agent 生命周期不稳），**两个不同阶段**（未起 vs 中途掉）。

### Q2：失败在"agent 启动前"还是"Hub 状态判断错"？
**两者都有成分，但主因是前者（事实）**：
- `never_started`（5/10）：**agent 启动前失败**（进程没起）——纯执行侧；
- `agent_offline`（5/10）：回收时 agent 状态为 OFFLINE。**注意**：这些 run 的 progress 多为 50（曾心跳）→ 说明 **Hub 的 `agent.status` 判 OFFLINE 参与了回收判定**（`_mark_stale_agents` 180s 无 agent 级心跳 → OFFLINE → 回收 run 窗口收紧到 120s）。
- **关键存疑**：`agent_offline` 的 run 中，**agent 级心跳离线**是否等价于 **run 真的死了**？——`progress=50` 的 run 可能仍在跑，却被 agent-OFFLINE 收紧窗口误回收。**这是最需要后续验证的一点**（属推断，非结论）。

### Q3：requeue 后第二次为何成功？
**证据（事实）——时间间隔是线索**：
| task | 失败 | 第二次(成功) | 间隔 |
|---|---|---|---|
| 6bd57c29 | offline → never_started | 08:54:20 OK | +49s |
| 9943f076 | offline | 09:14:00 OK | +58s |
| f0ec340b | offline | 09:51:21 OK | +28s |
| ad059149 | offline → never_started | 10:28:59 OK | +23s |
| e59b8096 | OK | (d7e86345 never_started) | — |

- **成功重试多在失败后 20~60s**（一次退避周期）；
- **推断**：**opencode 会话首次启动慢/失败，重试时进程状态更干净 → 成功**。即 **首次启动未就绪，重试即好**；
- **诚实边界**：无法从 DB 直接证明"第二次启动更顺利"（缺 agent 启动日志）；此为**基于时间模式的推断**。

### Q4：失败是否集中在某 worker / 时间窗 / Hub 重启前后？
**不集中，但见两处聚集（事实）**：
- **agent**：`opencode`(11) + `idle-worker-opencode`(6) 为主（cohort 用的是 idle-worker-opencode）；
- **时间**：cohort 失败尝试集中在 **10-02 08:24 ~ 10:28**（约 2 小时窗口）+ 早期 8-9 月；
- **Hub 重启**：**10-02 这次 hub 崩溃/重启**，其后仍有失败（非重启专属）；
- **结论**：**非单一 worker/单一时间窗/非重启专属**——是**持续性的低概率（~40%）首次失败**，与 agent 启动环境相关。

---

## 3. 关键指标（回答"首次失败率/自愈率/额外成本"）

| 指标 | 值 | 说明 |
|---|---|---|
| **首次启动失败率** | **10/26 ≈ 38%** | cohort 内 26 次 run 中 10 次失败（注：含重试 run，分母为总 run） |
| 更准确：**任务首次失败率** | **~6/16 ≈ 38%** | 16 任务中约 6 个首次尝试失败 |
| **requeue 自愈率** | **100%** | 所有失败任务经重试**最终全部成功** |
| **额外 run 成本** | **25 / 16 = 1.56 run/task** | 即 +56% run 开销 |
| **额外延迟** | 成功重试在失败后 **20~60s** | 一次退避周期 |

---

## 4. 判定：transient failure 还是 P1 工程缺陷？

| 维度 | 观察 | 倾向 |
|---|---|---|
| 自愈 | 100% 自愈 | 像 transient |
| 频率 | **~38% 首次失败** | **偏高**（非偶发） |
| 成本 | +56% run、+20~60s/失败 | 可感知但可控 |
| 是否掩盖问题 | **是**——最终 100% 掩盖了首次 62% | **需警惕** |

**判定**：**介于两者之间——"系统级可容忍的 transient（有自愈），但频率高到值得记为 P1 观察项"**。
- **不立即修**（按裁定）；
- **但不应长期容忍**：38% 首次失败意味着**若不重试，真实一次成功率仅 ~62%**。

---

## 5. 最需后续验证的存疑点（推断，未证明）

1. **`agent_offline` 是否误回收 `progress=50` 的活跃 run**？——agent 级心跳离线 ≠ run 级死亡；窗口被 `min(timeout, 120)` 收紧可能误杀。**需 agent 启动日志才能定论**；
2. **首次失败的真实原因**：opencode 会话启动失败？MCP 握手慢？——**缺 agent 侧日志**；
3. **重试成功是否只因"退避后环境更干净"**——推断，需实验。

## 7. 结论

> **系统瓶颈 = Agent 生命周期可靠性（首次调度 ~62% 一次成功、38% 需重试），而非任务协议。**
> **系统具备 100% 自愈能力**（重试兜底），**但同时用重试掩盖了首次调度不稳定**。
> **下一步决策**：是否将"首次启动失败率"列为 P1 观察项 / 是否补 agent 启动日志以定论存疑点——**待技术负责人裁定**。
