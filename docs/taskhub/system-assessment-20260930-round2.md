## 2. 系统真实能力

### 已真正实现（有数据/测试证明）
- 任务生命周期状态机 + 原子认领（乐观锁）——**并已通过真实并发 E2E 证明**（10×100 零重复）；
- 文档链门控（ReadEvidence 30 条）+ 阶段质量门 + 棘轮基线；
- 心跳超时回收 + **窗口自适应 + never_started 有界 requeue**（新代码，测试覆盖）；
- 定时任务 cron（104 次执行记录）；
- 事件日志（157 task_created 等，20+ 类型）；
- **洞察消费环（P2-4 新增）**：critical insight → 跟进任务（remediation 2 条实证）；
- 空转治理（P1-1）：消费意愿 guard + 99 条归档；
- 真实服务 E2E（4 用例）+ 并发压测（P50 30.5ms / P95 32.5ms）。

### 部分实现
- 事务性 outbox：**真实在用**（ADR→Git 同步链），但生产 0 行（未触发/已清理）；
- 多 agent 接入：16 个不同 agent 名有 run（opencode 78 / codex 19），但**绝大多数为一次性冒烟标识**（re-smoke/th1/th2/probe 等），真实常态使用的只有 opencode/codex；
- 默认鉴权：代码存在（Bearer/token），但**默认关闭**。

### 尚未证明（关键）
- 心跳修复的**实际效果**：生产 24 次 heartbeat_timeout 全是修复前历史，**无修复后新样本** → "假失败归零"**未被证明**；

- 真实 agent 进程 E2E（P1-4 用 HTTP 模拟 agent，未跑真实子进程）；
- 跨进程并发、>100 规模、多租户。

## 3. 核心价值判断

### 3.1 解决什么问题
多 AI agent 协同时，缺少"谁在干什么、干到哪、产出物在哪、能否验收"的统一**任务编排 + 证据留痕层**。

### 3.2 是否形成价值闭环

**本轮首次观察到闭环成立的具体证据**（对比第一轮的"断裂"）：

```
idea(40) → 被拆解(35, 87.5%) → task → run(90/289) → 完成(64)
                    ↓
        metrics → insight(3) → [P2-4 新增] → 跟进 task(2) → ?待处理
```

- **良性证据**：40 个 idea 中 **35 个被拆解成 task**（87.5% 转化率）——远超第一轮"20 个 NEW 无人处理"的印象；
- **新闭环**：insight → task 的消费路径已通（remediation 2 条），**但末端未闭合**（跟进任务未被处理）；
- **仍存断点**：289 task 只有 90 有 run（**69% 任务从未被任何 agent 执行**）——这是**最大的价值损耗点**。

### 3.3 AI 是否真正必要

| 环节 | 判断 | 理由 |
|---|---|---|
| agent 执行代码任务 | **必要** | LLM 不可替代 |
| 洞察消费（P2-4） | **已改为确定性** | 阈值判定 → 建任务，无 LLM（正确方向） |
| 空转治理（P1-1） | **已改为确定性** | 堆积计数 → 跳生成，无 LLM（正确方向） |
| 定时创意生成 | **已关闭** | 第一轮判定的方向性偏差已纠正 |
| 心跳/窗口/重试 | **确定性** | 状态机 + 计数，无 LLM（正确） |

**结论**：本轮最重要的进步不是"加了 AI"，而是**把 3 处本不该用 LLM 的环节改回了确定性机制**（洞察消费、空转治理、定时生成关闭）。这正对应第一轮指出的方向性偏差。

## 4. 架构评估

### 优点
- 分层可辨（api/workflow/models/observability/scheduling）；
- 状态机显式集中；乐观锁经**真实并发验证**；
- 新增模块（insight_remediator）职责单一、可关闭、可观测；
- 真实 E2E 落地（起真服务）。

### 缺陷（结构性，与第一轮一致）
1. **API 层直连 ORM**：仍无 Repository 层（32 api 文件直接 `db.commit()`）——**已评估：暂不重构**（E2E 未暴露问题）；
2. **`TaskStage.CANCELLED` 双语义**（models.py:43）——留档；
3. **迁移漂移**（agent.session_count 代码/库不一致）——留档。

### 最大结构性风险
**不是并发，而是「无人消费」**：289 task → 90 run（**69% 从未执行**），77 QUEUED 未认领。系统**生产任务的速率远超消费任务的速率**。这是**产品/运营问题，而非架构问题**——架构支持得很好，但没有人（或 agent）来干这些活。

### 扩展风险
| 维度 | 级别 |
|---|---|
| 新 agent | 配置级 |
| 新任务类型 | 配置级 |
| 新工作流状态 | 代码级（`can_transition` 硬编码） |
| 新租户 | 架构重构 |

## 6. 可靠性评估

> **如果系统出现异常，会不会进入错误状态？**

**本轮答案（较第一轮更精确）**：
- **心跳**：根因已定位（never_started 非误判）+ 修复（窗口自适应 + 有界 requeue）。**推断**修复有效（测试覆盖），**但生产无修复后样本** → 效果未证实；
- **事件一致性**：两条机制均**事务内持久化**，失败注入 4 场景证明广播失败不影响 commit；
- **恢复链**：Detect（超时回收）→ Classify（never_started/offline/timeout）→ Recover（requeue/FAILED）→ **Verify（P1-2 新增 refresh 校验）**——四级闭环**已补齐**（第一轮缺 Verify）；
- **仍然**：`except: pass` 静默失败在关键路径（心跳/审计/池）存在（本轮统计 `except Exception: pass` **0 处**匹配——**说明已大量收敛**，但广播/审计仍有静默吞异常）。

## 9. P0 / P1 / P2 / P3 问题

### P0（致命）
**（仍无确证 P0）**——无数据损坏/状态不可信/核心不可用的证据。

### P1（严重）

**P1-A 默认无鉴权 + 默认 bind 0.0.0.0**（本轮新发现，安全） ✅ **【2026-09-30 已结，task 3b5128b6：默认 loopback + 非环回拒绝 + SSRF guard】**
- **问题**：`app.state.auth_token = env or ""`，空 token = 不鉴权；`--host` 默认 `0.0.0.0`（所有网卡）。实测无 token 可 POST 建任务（本地 200）。
- **影响**：若以默认参数在**联网机器**启动，局域网内任意主机可读写任务库（建/改/删任务、读文档）。
- **证据（事实）**：main.py:433 `default="0.0.0.0"`；main.py:328 token 可空；实测 `POST /api/v1/tasks` 无 token → 200。
- **缓解事实**：**当前运行实例绑定 127.0.0.1**（Get-NetTCPConnection 实测 LocalAddress=127.0.0.1）——即 tray/launcher 未用 0.0.0.0 默认。
- **修复建议**：默认 host 改 `127.0.0.1`；或 token 为空时**拒绝非 loopback 来源**；启动时打印安全警告。
- **优先级**：高（潜在；当前实例因 loopback 未暴露）

**P1-B 任务消费率低（69% 任务从未执行）**（本轮重大发现，非架构）  【部分处理：task 5d4c8b68 已修正归档语义（队列除去 6 条归档垃圾，候选池 39→33）；剩余主体是「无活跃消费者」，属运营层，见下】
- **问题**：289 task 中仅 90 有 run；77 QUEUED 未认领。
- **影响**：系统在"生产任务"而非"完成任务"，价值未兑现。
- **证据（事实）**：`SELECT COUNT(DISTINCT task_id) FROM run`=90 vs task=289。
- **修复建议**：清理无用任务 / 让空闲 worker 真正消费 / 收敛任务创建来源。
- **优先级**：高（**价值层面**，非可靠性）

### P2（重要优化）
- **P2-A webhook SSRF 无白名单**）✅ **【2026-09-30 已结，task 3b5128b6】** 原文：cron webhook 可打任意 URL（含内网元数据地址）。**证据**：`_fire_webhook` 直接 `httpx.Client.request(url)`，无 host 校验。建议：内网/环回地址默认拒绝或需显式允许；
- **P2-B API 直连 ORM**（留档，暂不重构）；
- **P2-C `CANCELLED` 双语义 + 迁移漂移**（留档）。

### P3（普通）
- `TestClient` 仍是测试主流（113 处）；
- 广播/审计路径静默吞异常；
- 中文编码历史包袱。

## 10. 最关键的 5 个问题（按风险/依赖排序）

1. **P1-A 默认无鉴权 + 0.0.0.0**——**安全风险，一旦联网部署即暴露**，且修复成本极低（改默认值）。**优先级最高**。
2. **P1-B 任务消费率 31%**——**价值兑现问题**：系统造的任务没人干。**决定项目是否真有价值**。
3. **修复后的效果验证**（心跳 / 洞察闭环）——目前只有"代码+测试支持"，**缺生产真实样本**。没有它，前两轮修复的成效仍是推断。
4. **P2-A webhook SSRF**——与 P1-A 同属"默认不安全"，一并修。
5. **测试覆盖真实层扩展**（真实 agent 进程 / 跨进程 / 规模）——决定能否宣称"生产级"。

**为什么这个顺序**：1、4 是**安全**（低成本高收益，且是外部暴露面）；2 是**价值**（决定系统存在意义）；3 是**验证**（把"推断"变"事实"）；5 是**成熟度**（长期）。

## 11. 下一阶段路线

### 阶段一：堵安全默认值（现在 → 必须补齐）
- **目标**：消除"默认不安全"
- **工作**：默认 host=127.0.0.1；token 空时拒绝非 loopback；webhook 拒绝环回/内网地址（或需白名单）；启动打印警告
- **验收**：默认启动仅 loopback 可达；无 token 时非本机请求 403

### 阶段二：提升任务消费率（必须补齐 → 验证）
- **目标**：让任务真正被执行
- **工作**：清理陈旧 QUEUED；空闲 worker 上线（`idle_worker` 已有）；收敛自动建任务
- **验收**：消费率（有 run/task）> 60%；QUEUED 未认领 < 20

### 阶段三：效果验证（验证 → 稳定）
- **目标**：把修复从"推断"变"事实"
- **工作**：真实 agent 长任务（验证心跳）；真实处理一个 `[insight]` 任务（验证闭环末端）
- **验收**：修复后 heartbeat_timeout 有对照样本；洞察跟进任务被实际处理

### 阶段四：生产化（稳定 → 生产化）
- **目标**：可交付他人
- **工作**：Repository 层（若触发条件满足）；真实 agent E2E；多租户评估
- **验收**：新开发者 1 天理解；`MIO_DOC_GATE_STRICT=1` 全绿
