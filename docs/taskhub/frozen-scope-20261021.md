# 冻结清单（Frozen Scope）· mio-taskhub

> 依据：`docs/taskhub/product-decision-20261020.md` §3「冻结清单」
> 日期：2026-10-21 ｜ 决策人：作者（单人项目）
> 生效方式：**代码不删、接口不删、文档保留**。冻结 = 停止投入、停止调度、停止当价值宣称、移出主链路。

## 为什么冻结

这个项目没有「发展空间」问题，有「**过度建设**」问题。
决策 §0 总原则：

> **会在「相当一部分合法完成」上触发的检查，只能「警告/标注」；只在「明确的失败或撒谎」上触发的检查，才配「拦截」。**

保留的唯一投入项是**窄门禁**（拦「假完成」）—— 它是唯一能把「完成」从「Agent 自报」变成「有硬证据」的改动。
其余全部冻结。

### 为什么「多入口合并」本轮不做

决策 §3 把它列为「合并收敛」，但本轮**不执行**，理由是证据与风险：

1. **两个阶段入口不是纯重复**：`advance_stage` 走 `can_advance` 做相邻推进校验；
   `move_to_stage` 允许任意跳转，需额外处理「从非 review 源挪到 review」的兜底路径
   （T5/T6 序列）。P1-2 实测时刚踩过同一个坑 —— `move` 需要把「无完成路径」的
   状态机判定**前置**到评审判据之前，而 `advance` 不需要。合并要重写状态机流转逻辑。
2. **无「维护成本是真实痛点」的证据**：决策 §5 复审条件第 2 条要求
   「作者能演示某个冻结项真的省了具体时间」——目前没有这类证据。
3. **与「先做减法」不冲突**：合并入口属**结构性改动**（要改核心状态机流转），
   风险高于它当下的收益；决策 §0 的总原则是「宁可门是哑的，不能门是堵的」，
   同理适用于「宁可两个入口并存，不要改坏状态机」。

**解冻条件**：出现具体的维护痛点证据（如同一处逻辑改动要同时改两处且已漏改过一次），
或决策清单被修订。届时按「先补测试再合并」的顺序做，不在本轮。

### 本轮实际关掉的两个调度（2026-10-21）

审计时发现两项冻结能力**仍在生产调度里跑**，「冻结」只停留在文档上：

| 能力 | 原默认 | 现默认 | 影响 |
|---|---|---|---|
| observer 机会发现自启 | **开**（`MIO_OBSERVER_AUTOSTART` 未设即启用） | **关** | 不再随 hub 启动拉起 observer 守护进程 |
| idea 自动评审扫描 | **开**（每 24 分钟建一批评审任务） | **关** | 不再自动扩张 idea 子系统 |

两处都保留了显式开启的开关（`MIO_OBSERVER_AUTOSTART=1` / `MIO_IDEA_REVIEW_ENABLED=1`），
解冻时不需改代码 —— 这是决策 §0「冻结 ≠ 删代码」的直接体现。

**未纳入冻结的项**（避免擅自扩大范围）：`MioDigestJob`（mio digest 写回）与
`ContractJob`（契约冒烟探针）默认仍开。这两项属 mio-intelligence 的**能力代理**，
不在决策 §3 的 8 项清单内，故本轮不动 —— 若判定它们也该冻结，需先扩决策清单。

## 三种「冻结」不是一回事

决策 §3 要求「停掉调度、移出主链路、改掉价值宣称」。逐项对照：

| 项 | 停调度 | 移出主链路 | 改宣称 | 现状 |
|---|---|---|---|---|
| creativity 调度 | ✅ 已停 | ✅ 无后台调用 | ✅ README 不作核心宣称 | 已完成 |
| observer 机会发现 | ✅ **本轮改默认关** | ✅ 不进主链路 | ✅ 同上 | **本轮完成** |
| Prometheus/SLO/tracing | — （无调度） | ⚠️ 端点仍在 | ✅ README 标注冻结 | **宣称已改，端点保留** |
| memory gateway | — | ⚠️ MCP 工具仍在 | ✅ README 标注冻结 | **宣称已改，工具保留** |
| ADR 投影 | — | ⚠️ GitSync 仍在投影 | ✅ README 标注冻结 | **宣称已改，投影保留** |
| idea 子系统 | ✅ **本轮改默认关** | ⚠️ 端点仍在 | ✅ README 标注 | **本轮停调度，端点保留** |

**「移出主链路」的判定口径**：一个能力是否算「在主链路上」，看**它是否被 taskhub 的核心闭环（claim → 执行 → 评审 → done）自动依赖**。
按此口径，上述五项**都不在核心闭环上** —— 它们都是旁路增强能力（看板/记忆/文档投影/指标），
核心闭环不依赖它们的产出。因此「移出主链路」在这五项上**已经成立**，
无需改代码；剩下的动作只有「改宣称」。

## 复审条件（决策 §5）

1. 窄门禁频繁误伤合法完成 → 回退为「仅标注」（**不加严**）
2. 作者能演示某个冻结项真的省了具体时间 → 对应条目解冻，决策按证据修订
3. 诚实记账后发现运行失败主因是口径失真而非真实故障 → 可靠性判断上修
4. 出现第二个真实用户 → 重新评估 SLO/tracing 等「多用户才成立」的冻结项

## 第 4 步「观察一个真实周期」的配套

决策 §6 第 4 步：「用 §1 验收第 4 条判断成败，再决定要不要动别的」。

- 观察记录：**`docs/taskhub/diff-gate-grayscale-log.md`**（指标 M1~M5 + 回退条件 + 切 block 前置条件）
- 数据来源：新增只读端点 `GET /api/v1/board/diff-gate-stats`
  （**纯统计，不参与任何流程判定**，与 `_delivery_quality` 同性质）
- 唯一成功判据（决策 §1 验收第 4 条）：**能指着一例「它拦下了一次我本会放过的假完成」**

这个端点属**唯一保留项（窄门禁）的必要配套**，不违反冻结原则 ——
它服务于「判断唯一投入项是否真的产生价值」，本身就是决策要求的观察手段。
冻结的是那些「无证据的扩张」，不是「验证唯一投入项的手段」。
