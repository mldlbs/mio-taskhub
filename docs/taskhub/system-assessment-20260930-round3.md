## 3. 核心价值判断

### 3.1 解决什么问题
多 AI agent 协同时，统一的**任务编排 + 证据留痕**层。

### 3.2 是否形成价值闭环
```
idea(40) → 拆解(35, 87.5%) → task(292) → run(95/292=32.5%) → 完成(67)
                              ↓ 最大断点：67.5% 任务无 run
        metrics → insight(3) → [P2-4] → 跟进 task(2) → ❌ attempt 1/2 仍 QUEUED
```
- **良性**：idea→task 转化 87.5%；
- **新闭环已通但末端未闭**：洞察消费路径存在，但跟进任务仍未被处理；
- **最大断点**：**消费率 32.5%**（系统性造任务、无消费者）。

### 3.3 AI 是否真正必要
维持第二轮判断：**执行用 LLM（必要），分析/治理改确定性（已做）**。本轮新增观察：**MCP 工具面（19 个写/破坏性）是 agent 的真正能力载体，但也带来 tool-abuse 面（见 §7）**。

## 4. 架构评估

**优点**：分层可辨；状态机集中；乐观锁经真实并发验证；新增模块（net_guard/insight_remediator）职责单一。

**缺陷（本轮确认）**：
1. **API 直连 ORM**：`db.commit()` **59 处**（api 目录）——RUoW 留档（暂不重构，E2E 未暴露问题）；
2. `TaskStage.CANCELLED` 双语义（持久化专用，读时映射 BRAINSTORMING）；
3. 迁移漂移（agent.session_count）。

**最大结构性风险（维持）**：**不是并发，是"无人消费"**——292 task 仅 95 有 run。

**扩展风险**：新 agent/任务类型=配置级；新状态=代码级；新租户=架构重构。

## 9. P0 / P1 / P2 / P3 问题

### P0（致命）
**（仍无确证 P0）**——无数据损坏/不可恢复证据。

### P1（严重）

**P1-A 消费率 32.5%（价值兑现）**
- **问题**：292 task 仅 95 有 run（67.5% 从未执行）
- **影响**：系统在"造任务"非"干任务"
- **证据**：`COUNT(DISTINCT task_id) FROM run`=95 vs task=292
- **修复建议**：解决 agent 可用性（opencode CLI/充值 codex/换模型）→ 启用 idle_plan；收敛自动建任务
- **优先级**：高（价值层）

**P1-B ADR 渲染 XSS 缺口（新增）**
- **问题**：`IdeasView.jsx:1607` 用 `marked(adrMd.content)` 直接 `dangerouslySetInnerHTML`，**未过 DOMPurify**（DocPanel 正确净化，此处遗漏）
- **影响**：ADR 内容可由 agent 写入 → 存储型 XSS（本地单用户，风险中等；若导出/共享 ADR 则放大）
- **证据**：DocPanel.jsx:154 `DOMPurify.sanitize(marked.parse(...))` vs IdeasView.jsx:1607 无 sanitize
- **修复建议**：与 DocPanel 一致，`DOMPurify.sanitize(marked(...))`
- **优先级**：高（低成本，同类代码已有正确范式）

**P1-C 高风险 MCP 工具无策略门控（新增，agent 专属风险）**
- **问题**：19 个写/破坏性工具，仅 `cancel_task` 标 `destructive=True`；无统一的高风险确认/策略检查
- **影响**：agent 自主调用可静默执行写/删除操作（如 `remove_job`、`cancel_task`、批量更新），无审计门控
- **证据**：mcp_server.py 仅 1 处 `destructive=True`；`except` 无 risk gate
- **修复建议**：为写/破坏性工具加 `destructive=True` 标注 + 可选策略门控（复用 Mio 的 `policy_check` 理念）
- **优先级**：中（本地单用户当前风险有限，多 agent/远程场景上升）

**P1-D 心跳/洞察修复效果未验证**
- **问题**：修复是"代码+测试支持"，无生产新样本
- **影响**：修复成效仍是推断
- **证据**：heartbeat_timeout 24 条全为修复前；[insight] 任务仍 QUEUED
- **修复建议**：有可用 agent 后跑真实长任务 + 处理洞察任务
- **优先级**：高（验证闭环）

### P2（重要优化）
- **P2-A** API 直连 ORM（59 处 db.commit）→ RUoW（留档，暂不重构）
- **P2-B** `CANCELLED` 双语义 + 迁移漂移
- **P2-C** 事务性 outbox 生产 0 行（未触发/已清理，非缺陷）

### P3（普通）
- TestClient 仍主流（113 处）
- console.log 无轮转
- 中文编码历史包袱

## 10. 最关键的 5 个问题（按风险/依赖排序）

1. **P1-A 消费率 32.5%**——决定系统是否有价值（**运营+环境**，非纯代码）。
2. **P1-D 修复效果未验证**——把"推断"变"事实"的前提，依赖 P1-A 的 agent 可用性。
3. **P1-B ADR XSS**——低成本安全修复，同类代码已有正确范式。
4. **P1-C MCP 工具策略门控**——agent 系统的固有风险面。
5. **P2-A 事务边界**——长期可维护，可延后。

**排序依据**：1→2 是"价值兑现"链条（需外因）；3→4 是"安全"（低成本）；5 是长期项。

### 15.2 为什么冻结

**TaskHub 的问题已不是"还缺什么功能"，而是：**
> **已有机制能不能在真实 Agent 持续消费下产生可观测的业务价值。**

### 15.3 冻结范围

**冻结**：新增功能、P2/P3 小优化、架构重构（RUoW 等）。
**允许**：① 修复真实生产事故（P0/严重 P1）；② 与真实运行验证直接相关的改动；③ 文档。
