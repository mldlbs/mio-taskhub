## 1. 一句话结论

**工程化 MVP（自用工具），介于"可运行 MVP"与"工程化 MVP"之间。**

依据（事实）：
- 核心链路真实运行（278 任务 / 119 run），状态机与证据门控有数据支撑；
- `outboxevent` = 0：事务性发件箱设计存在但未启用，**当前事件一致性依赖"提交后广播"，缺乏事务性保证**（非"事件会丢"，见 §4.4）；
- **119 次 run 中 52 次 exit_code≠0**，其中 **24 次 `heartbeat_timeout`**——"心跳误判"为**推断**（见 §6），非已证明事实；
- 51% 任务是 CANCELLED，97/142 来自同一个定时任务（**方向性问题 / 资源浪费**，非数据损坏，故定为 P1，见 §9）；
- 969 个测试全是 `TestClient` 进程内桩，**无真实环境 E2E**。

距离"生产候选"的主要差距不是功能，而是**可靠性验证与数据可信度**。

## 3. 核心价值判断

### 3.1 它解决什么问题

多 AI agent（opencode/codex/hermes）协作时，缺少"谁在干什么、干到哪、产出物在哪、能否验收"的统一**任务编排 + 证据留痕**层。

```
用户/定时器
 ↓ 建任务(title + acceptance_criteria + doc_paths)
待领取队列 (stage=ready)
 ↓ agent claim（原子抢占 + run_id）
执行（心跳保活）
 ↓ submit_result（**ReadEvidence 指纹门控** ← 真差异化机制）
阶段推进（doc approved + 质量分≥80 + 棘轮基线）
 ↓
完成 → 事件流 → 看板/拓扑
 ↓
memory/observer 记录（**这一环薄弱**）
```

### 3.2 是否形成价值闭环

**部分闭环，存在断点**（事实 + 推断）：

- **良性闭环**：ReadEvidence 门控确实改变 agent 行为——强制"先读 spec/api 再写码"，30 条 evidence 为证。
- **断裂闭环**：`统计 → 分析 → 洞察` 的产物没有回头改变行为——`insight` 3 条 vs `depmetrics` 19109 条。**这是"计算闭环 ≠ 价值闭环"的典型案例**：指标算出但无人消费。
- **自我制造垃圾**：97 个定时任务几乎无人认领即被取消（仅 5 个 claim）。

### 3.3 AI 是否真正必要

| 环节 | 判断 | 理由 |
|---|---|---|
| agent 写码 | **必要** | LLM 不可替代 |
| 定时想法生成 | **不必要却用了** | 97 任务空转；insight 3 条；idea 40 条中 20 条 NEW 无人处理 |
| `next_action` 规则引擎 | **好的确定性设计** | 8 条显式规则 |
| 409 重试三档 | **LLM 挤占确定性** | 素材重复本可用去重 + 门控 |

**方向性问题**：用 LLM 全自动链路解决本可用"确定性触发 + 人工确认"解决的问题，**这是当前最大的方向性偏差**。

## 4. 架构评估

### 4.1 分层

```
web (React 45 files)
 ↓
api (32 modules, FastAPI)
 ↓  ← 直接操作 ORM（db.commit/db.add）
workflow (state_machine / transitions)
 ↓
models.py (SQLModel 486 行) + db.py (SQLite WAL)
```

### 4.2 优点

- 模块职责可辨（32 个 api 文件按领域切分）；
- 状态机显式集中（`models.py` + `workflow/transitions.py`）；
- WAL + 乐观锁选型对单机合理；
- 中间件齐全（auth / rate-limit / request-id / charset）。

### 4.3 缺陷（结构性）

1. **API 层直连 ORM**：`db.commit()` 遍布 32 个 api 文件，**无 Repository/Domain 层**，事务边界散落（事实）。
2. **一进程多职责**：FastAPI + 托盘 UI + 后台线程池 + cron + git-sync + observer autostart 全在 `main.py:lifespan`。
3. **状态语义不一致**：`TaskStage.CANCELLED` 是"持久化专用 hack"（`models.py:43` 自认注释），读时映射回 `BRAINSTORMING`。
4. **迁移漂移**：`agent.session_count` 代码有库无。

### 4.4 最大结构性风险

**缺少统一事务边界（无 SSOT）**：乐观锁仅在 claim 路径正确；`execute_replace` / 多线程广播 / cron 三处并发写同一 SQLite，靠 5s busy_timeout 兜底（推断：高并发下会出现 `database is locked`）。

**事件一致性模型现状**：~~`OutboxEvent`=0，未使用事务发件箱；实际走**提交后广播**~~ **【2026-09-30 c32a2145 纠正】** 系统有**两条独立机制**：(A) 任务事件=**事务内持久化**（`emit_event` 与业务同 `db.commit()`）+ 提交后尽力 WS 广播；(B) ADR→Git=**标准事务性 outbox**（`OutboxEvent`，adr.py 同事务写 + git_sync.py 重试投递）。**结论：不存在"事件会丢失"**——两者持久化都在事务内，WS 推送失败只是"尽力投递"的固有语义（失败注入 4 场景实测，见 docs/taskhub/event-consistency-model.md）。唯一加固点：`_broadcast_after_commit` 已改为逐事件 try/except，防广播异常反向冒泡出已提交的 commit()。

### 4.5 扩展风险

| 扩展维度 | 级别 |
|---|---|
| 新 agent | 配置级（`agent_type` 已支持） |
| 新任务类型 | 配置级 |
| 新工作流状态 | **代码级**（`can_transition` 硬编码 dict） |
| 新数据源 | 配置级（observer/collect） |
| 新 UI | 配置级（React 组件） |
| 新租户 | **架构重构**（无 tenant 维度） |

## 6. 可靠性评估

> **如果系统出现异常，会不会进入错误状态？** —— **会进入"难以区分真失败与假失败"的状态。**

### 6.1 心跳超时：能证明什么、不能证明什么

**事实（可证明）**：
- 119 次 run 中 52 次 failed，其中 **24 次 `heartbeat_timeout`**；
- 24 次超时的运行时长**高度集中于 ~120–130s**（14 次落在 120.1–129.7s），另有 1748s / 3873s 两个长尾；
- 受影响任务的 `est_duration_min` 为 30 / 90 / 120 / 180，但**回收窗口固定 180s，未按 `est_duration_min` 自适应**（`background.py AGENT_TIMEOUT_SECONDS=180`）；
- 超时后部分任务**最终仍被完成**（5 个 task 状态 COMPLETED/DONE），部分停留在 QUEUED/IMPLEMENTING——**说明部分"失败"并非真实失败**。

**推断（尚无完整证明）**：
- "心跳被误判"是**推断**：120–130s 的硬边界强烈提示存在一个固定时间窗缺陷（可能是 agent 生命周期管理，而非任务本身失败），但**无法证明 agent 在 cutoff 时仍然活着**——缺心跳时序与 agent 存活日志。
- 因此「误判」必须标注为待验证假设，不能写成结论。

### 6.2 恢复机制
- 有 Detect（超时回收）+ Classify（`_is_system_timeout_failure`）+ 部分 Recover（requeue 20 次），但**无 Verify 环节**——requeue 后不校验是否真的恢复。
- **并发**：乐观锁优于裸读写，但非全路径；19109 条指标写入与业务写共享 SQLite。
- **输入异常**：Pydantic 覆盖请求校验（好）；但前端曾 `JSON.parse` 静默吞异常——"静默失败"是系统性习惯。

## 7. AI / Agent 评估

### Agent 的价值在哪里

- **在执行**：让不同 CLI agent 共享任务队列与证据账本——真实价值，只有多 agent 场景才成立。
- **不在思考**：创意识别、指标分析目前被 LLM 承担但无价值证据。

### 应改为确定性机制的地方（直接建议）

1. **定时想法生成** → "确定性触发 + 人工确认后才建任务"，或停掉（97/102 空转）。
2. **指标→洞察** → 改用**阈值告警规则**（`alertrule` 表已在）。
3. **409 死循环** → 确定性去重 + 新素材门控。

### 应继续用 LLM 的地方

- agent 写码、代码审查建议、`next_action` 的自然语言解释。

## 8. 测试可信度

### 测试证明了什么
单元/集成级正确性——969 passed 证明"模块在进程内、桩数据下行为正确"。状态机、门控、API 契约有覆盖。

### 测试没有证明什么

- **无并发测试**：无多线程同时 claim 的用例。
- **无真实 LLM/agent 路径测试**：全 mock。
- **无数据规模测试**：生产 278 任务，测试用空库。
- **无对照实验/量化指标**：无 A/B、无成功率基线。

### 还缺的真实实验
1. 10 agent 并发 claim 100 任务的**不重复性**压测；
2. 长任务（>180s）心跳窗口适配验证；
3. 真实 agent 跑通"建单→完成"全链并核对 evidence 指纹。

## 9. P0 / P1 / P2 / P3 问题

> **P0 的判据**：导致数据损坏、状态不可信、核心功能不可用、无法恢复。
> 按此判据，**当前系统没有确证的 P0**——最严重的问题是可靠性基线未建立与资源浪费，属 P1。

### P0（致命）

**（当前空缺）**——没有证据表明存在数据损坏或核心功能不可用。若 §6.1 的"心跳误判"被证实为**状态写入错误**（如把仍在运行的任务判为 failed 并释放资源给重复认领），则升级为 P0；在此之前不列。

### P1（严重）

**P1-1 定时任务空转（方向性问题 / 资源浪费）**
- **问题**：定时任务无"下游消费意愿"检查，每天自动建任务又取消
- **影响**：97/142 取消任务、污染看板与指标、浪费 LLM 调用（**不导致数据损坏**，故为 P1 而非 P0）
- **证据**：task 表 title 分布；97 个仅 5 个被 claim
- **修复建议**：加"下游消费意愿"开关 / 改人工确认制；清理历史
- **优先级**：最高（P1 内）

**P1-2 心跳超时占比高，真/假失败无法区分**
- **影响**：119 run 中 52 failed，其中 24 heartbeat_timeout；看板成功率不可信
- **证据**：run 52 fail / 24 heartbeat_timeout；时长集中于 120–130s；窗口固定 180s 未自适应
- **修复建议**：**先做根因定位**（心跳时序 + agent 存活日志），再决定窗口自适应或生命周期修复
- **优先级**：高

**P1-3 事件一致性模型未明确** ✅ **【2026-09-30 已结，task c32a2145】**
- **原影响**：模型不清晰，可能被误判为"事件会丢失"
- **原证据**：outboxevent=0；event 表 1429 行
- **处置结果**：审计确认两条机制（任务事件=事务内持久化+尽力广播；ADR→Git=标准 outbox），**不存在丢失风险**；产出 event-consistency-model.md；防御性加固 `_broadcast_after_commit`。**原判断"outbox 悬空死代码"经审计否定**（它是 ADR 同步链正常组件）
- **优先级**：已结

**P1-4 无真实 E2E / 无并发验证**
- **影响**：可靠性无法证明
- **证据**：test_integration.py 用 TestClient
- **修复建议**：新增真服务 + 并发 claim 测试
- **优先级**：高

### P2（重要优化）

- **P2-1** API 层直连 ORM，无事务边界 → 加 Repository/UnitOfWork（**架构债务，非当前最短路径，见 §11**）
- **P2-2** `TaskStage.CANCELLED` 双语义 hack → 分离持久化状态与展示状态
- **P2-3** 迁移与 models 漂移（`session_count`）→ 加 schema 校验测试
- **P2-4** insight 产物不被消费 → 接 `alertrule` 阈值规则

### P3（普通）

- 前端静默 `catch{}` 习惯（部分已修）
- 中文编码历史包袱
- `console.log` 单文件 16MB 无轮转（推断）

## 10. 最关键的 5 个问题（按风险/依赖排序）

1. **定时任务空转（P1-1）**——先止血，否则后续所有指标被垃圾污染，是其他修复的前提。
2. **心跳：真/假失败无法区分（P1-2）**——先做根因定位，是"状态是否可信"的核心。
3. **事件一致性模型未明确（P1-3）**——决定"数据是否可信"，可靠性地基。
4. **真实 E2E + 并发验证（P1-4）**——没有它，任何"可靠性"宣称都只是假设。
5. **API 事务边界（P2-1）**——长期结构性风险，**不阻塞前四项**，按 §11 推迟。

**排序依据**：1→2→3 是**数据可信度**的递进依赖；4 是**验证能力**；5 是**长期可维护**，可延后。

---

## 11. 下一阶段路线

> **路线原则**：先建立**可信运行基线**，再决定是否扩展（含结构性重构）。**Repository/UnitOfWork 不在当前最短路径**——它是架构债务，但优先证明核心运行模型可靠，收益更高。

### 阶段一：停止垃圾任务（止血）
- **目标**：停止制造噪声，让指标可信
- **工作**：关停/改造自动创意任务（含"每日数据同步"等所有自动建任务链路）；清理 97 条历史
- **验收**：连续 3 天新增 CANCELLED 自动任务 < 5

### 阶段二：查清 heartbeat failure（根因定位）
- **目标**：区分真失败与假失败
- **工作**：补心跳时序日志 + agent 存活日志；判定 120–130s 硬边界成因；**结论产出后**再决定窗口自适应或生命周期修复
- **验收**：能对每一类 heartbeat_timeout 给出"真/假"判定，并附证据

### 阶段三：明确事件一致性模型
- **目标**：消除"有表无数据"的悬空设计
- **工作**：审计提交后广播的失败恢复路径；决定"接入 outbox"或"文档化广播语义"（二选一，不必立刻接 outbox）
- **验收**：事件一致性模型有明确文档 + 至少一个失败注入测试

### 阶段四：真 E2E + 并发实验
- **目标**：从"代码支持"到"运行证明"
- **工作**：真服务 E2E；10 agent × 100 任务并发 claim；量化成功率/P50/P95
- **验收**：并发零重复认领被证明；成功率基线建立

### 阶段五：根据实验结果决定是否重构
- **目标**：数据驱动决定架构投入
- **工作**：若阶段四暴露事务边界问题，再做 RUoW；否则延后
- **验收**：重构决策有实验依据，而非"看起来该做"
