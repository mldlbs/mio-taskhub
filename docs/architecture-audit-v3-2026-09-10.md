## 第一部分：系统定位分析

**系统定位：** 本地单用户 Agent 协调基础设施

**当前架构阶段：** 稳定期

**目标阶段：** 稳定期 + 适度扩展

**架构成熟度：** Level 4/5（正式状态机 + 自动备份 + 容器化 + 全局限流 + 拆分重构 + 测试覆盖）

**架构与业务匹配度：** 架构复杂度与业务需求高度匹配。P2 修复后，系统的可维护性进一步改善。但仍有 2 个 God File 存在。

## 第二部分：核心架构决策审查

| 设计决策 | 收益 | 成本 | 风险 | 评价 |
|----------|------|------|------|------|
| SQLite + WAL + QueuePool | 零运维、本地优先 | 并发受限 | 规模增长时迁移 | ✅ 正确 |
| 统一状态机（ORM 枚举为权威） | 消除重复定义 | 27 个桥接调用点 | 低 | ✅ 正确 |
| SQLite Online Backup | 一致性强 snapshot | 每小时 IO 开销 | 低 | ✅ 正确 |
| Docker 多阶段构建 | 零安装部署 | 构建时间增加 | 低 | ✅ 正确 |
| 全局 API 限流（120 req/min） | 防止滥用 | 测试需要重置 | 低 | ✅ 正确 |
| tasks.py 拆分 | 可维护性提升 | 路由顺序需注意 | 低 | ✅ 正确 |
| MCP Server 代理模式 | Agent 通信标准化 | 921 行薄代理 | 维护成本 | ⚠️ P3 |
| 6 个后台守护线程 | 功能完整 | 无协调机制 | 无 | ⚠️ P3 |

### 技术驱动设计审查

**仍存在：** `mcp_server.py` 的 921 行是薄代理层。这是"为了标准化 Agent 通信"而引入的重复代码。理想方案是从 OpenAPI spec 自动生成或用代码生成工具。

### 不足设计

**6 个后台线程无协调机制**是最被低估的问题。当前 6 个守护线程（backup、cron、git-sync、heartbeat、night-runner、scheduler）各自独立运行，没有统一的协调机制。如果线程间出现资源竞争或状态不一致，调试将极其困难。

## 第三部分：架构风格分析

**当前架构：** 模块化单体 + 事件驱动组件

### 优点
- 单进程部署简单，调试方便
- 模块边界清晰（tasks.py 已拆分）
- 事件驱动解耦了通知和业务逻辑
- 自动备份 + 容器化 + 全局限流

### 缺点
- 所有后台任务共享进程，一个崩溃全部停止
- SQLite 单文件限制并发
- 921 行的 MCP 代理层维护成本高
- 6 个线程无统一协调

### 适用性评估

| 维度 | 评估 |
|------|------|
| 当前规模（1-5 agents） | ✅ 完全适用 |
| 未来增长（10+ agents） | ⚠️ 需迁移 PostgreSQL |
| 团队能力（小团队） | ✅ 可维护 |
| 运维能力（本地/容器） | ✅ 已支持 Docker |

## 第九部分：性能架构分析

### 完整请求链路

```
Client (React SPA)
  ↓ HTTP/WebSocket
FastAPI (sync endpoints in threadpool)
  ↓ SQLModel ORM
SQLite (WAL mode, QueuePool 5-15)
  ↓ (optional)
External: MCP Server / Git / Webhook
```

### 性能瓶颈 TOP 10

| # | 位置 | 瓶颈原因 | 影响 | 优化 |
|---|------|----------|------|------|
| 1 | mcp_server.py | 34 个 MCP 工具，每个 HTTP 往返 | Agent 延迟 | 从 OpenAPI 生成 |

## 第十七部分：CTO 最终结论

### 架构最大优势

**状态机驱动的业务规则不可绕过 + 自动备份 + 全局限流 + tasks.py 拆分。** 21 种显式转换 + 验证器确保了所有状态变更严格校验。SQLite Online Backup API 保证了数据安全。全局限流防止 API 滥用。tasks.py 从 700 行拆分为 4 个模块，大幅降低维护成本。这是系统最核心的四个架构决策。

### 当前最大风险

**`mcp_server.py` 的 921 行持续膨胀。** 每次新增 MCP 工具都意味着 20 行重复的 HTTP 转发代码。这是当前最容易被忽视但影响最大的技术债。

### 最错误的三个设计

1. **`mcp_server.py` 921 行手动编写** —— 应从 OpenAPI spec 自动生成
2. **6 个后台线程无统一协调** —— 应引入 ThreadRegistry 或统一调度器
3. **`advance_stage` / `move_to_stage` 重复** —— DRY 违反，应提取共享逻辑

### 最值得投入的三个优化方向

1. **P3：** 从 OpenAPI 自动生成 MCP 工具（2 天，消除 921 行重复代码）
2. **P3：** 统一后台线程调度器（1 天，消除资源竞争风险）
3. **P3：** 拆分 `api/ideas.py`（2 天，消除 641 行 God Controller）
